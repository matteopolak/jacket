# Compiler, VM and discovery benchmarks

## What it is

`jai-bench` measures compiler, module discovery, checked IR, interpreter and generated native-code performance across workload sizes. Latency and throughput are the primary comparisons; allocation counts/bytes, reallocations and maximum live Rust allocation footprint explain resource cost alongside them.

## How it works

The `whole_module` compiler cases share an independently authored mixed-feature module at 4, 64 and 1,024 handlers. Each reachable handler initializes a record and fixed array, indexes through a loop, selects an enum branch and returns a checksum contribution. The entry calls every handler, so native reachability does not discard the scaled workload. A closed-form checksum is checked by VM preflight before semantic/backend measurements. Source generation and fixture preparation happen outside stage timing. These are representative composed fixtures, not original-project compilation or comprehensive coverage of every source feature.

| Group | Timed work | Throughput unit |
| --- | --- | --- |
| `mixed_lex`, `mixed_parse` | Lexing or parsing the mixed source | Source bytes |
| `mixed_graph_load` | In-memory graph creation and parsing | Source bytes |
| `mixed_resolve` | Resolution of a prepared graph, including checked IR construction | Source bytes |
| `mixed_ir_verify` | Public procedure verification over a checked module | Source bytes |
| `mixed_lower_llvm` | Verified LLVM construction for all reachable handlers | Source bytes |
| `mixed_source_to_llvm` | Graph load, resolution, LLVM construction and serialization | Source bytes |
| `mixed_optimize_o0`, `mixed_optimize_o2` | Selected LLVM pass pipeline and verification on a fresh module clone | Source bytes |
| `mixed_object_o0`, `mixed_object_o2` | Machine code/object emission into memory from a prepared optimized module | Source bytes |
| VM `mixed_runtime_cold`, `mixed_runtime_reuse` | Execution in the explicit Runtime phase, in a fresh VM or following 40 successful warmups | Handler contributions |
| `mixed_native_batch_o0`, `mixed_native_batch_o2` | Execution of 256 checksum calls, including process startup and result checks | Logical handler contributions |

LLVM cloning stays outside optimization timing; object emission excludes semantic resolution, LLVM lowering, optimization and filesystem writes. The in-memory object must be nonempty. Native runtime cases freshly emit an authored Jai library and link it with an authored C harness using validated independently installed Clang 22. The harness varies the seed across 17 values and checks every call against its own integer checksum formula. Neither compiler/linker startup nor object emission is inside native execution timing. Each timed iteration starts a new process and asserts successful completion, so small workloads include substantial startup overhead; the result is batch latency and startup-inclusive throughput, not isolated nanoseconds per native function. The C harness is compiled separately without LTO, preventing it from constant-folding the external Jai function. O0/O2 refer to the Jai object's optimization, while the harness uses `-O2`. The throughput counter counts logical handler contributions: LLVM may inline handlers and simplify array/branch work, so it does not assert a physical native call or instruction count.

The shared preflight and mixed VM benchmarks use the explicit Runtime phase with the selected host's byte layout and allow 64,000,000 fuel for the mixed module; this is an explicit fixture resource limit, not a change to VM defaults. Every VM iteration checks its scalar checksum and that only one persistent default-context allocation remains. Preflight metadata records actual charged steps and calls. Native code has no interpreter fuel budget. Rust allocation rows for native runtime describe the parent process's launch/check overhead. They exclude child-process allocation, native LLVM heap, linked runtime memory and operating-system peak RSS. Do not describe Divan's maximum live Rust bytes as whole-process peak memory.

The runner launches each smoke or timed suite through a fresh `benchmark_resources.py` accounting process. `maximum_child_peak_rss_bytes` records the operating system's maximum individual waited child high-water RSS over the entire suite, including setup and native compiler/linker preparation. It is neither a per-iteration measurement nor simultaneous process-tree memory, and Clang preparation can dominate it. User/system CPU seconds are recorded separately. Known macOS byte and Linux KiB units are normalized explicitly; unsupported units fail. A timeout terminates the invocation's fresh process group and preserves an invalid run. Each native fixture also performs a separate successful resource preflight: the own C harness reads `getrusage(RUSAGE_SELF)` after its 256 checksum calls, and the workload metadata records `native_preflight_peak_rss_bytes`. This identifies the generated program's individual process peak without charging resource collection to the timed samples.

The coverage audit therefore distinguishes stage latency/throughput, host allocation diagnostics, OS process high-water memory and correctness/resource guards. Current limitations include process-startup-inclusive native runtime, suite-level rather than per-stage process RSS, no linked cross-target runtime benchmark, and no realistic original-project end-to-end benchmark. Existing type, source `#run`, discovery suspension, float alias, VM cold/reuse and explicit rejection cases remain complementary probes. A successful smoke validates the fixture; a timed baseline additionally requires an immutable checked runner artifact and completed measurements. The captured 107-case baseline below predates these mixed-module, optimization, object and native runtime cases, and does not validate or measure them.

The compiler suite's `float_aliases` cases measure pure exact constant aliases at 4, 64, and 128 doubling steps. Parsing the literal and repeated expression happens before timing. `weak_float_alias_build_and_round` binds a fresh alias DAG and performs its first `float64` rounding; `weak_float_alias_successful_round_reuse` uses an already successful per-width result. Every iteration checks the exact expected IEEE value. The existing Divan allocator profiler measures actual Rust allocation/deallocation/grow operations, rather than estimating work from the logical `2^n` leaf count. These cases exclude module discovery, VM execution, native compilation, and effectful expressions.

A focused ten-sample allocation diagnostic recorded 35, 455, and 903 Rust allocation operations for those three fresh-chain sizes, with about 2.36 KB, 32.6 KB, and 64.85 KB allocated. Successful-round reuse reported no allocation rows. [Raw output and component metadata](../artifacts/benchmarks/float-alias-dag-20261002T110027Z/results.txt) retain the copied benchmark executable's hash. This direct diagnostic did not freeze the whole source tree or rerun the dependency-age checker; it is descriptive allocation evidence, not an official baseline or timing comparison. Reuse timings approach the timer's resolution and should not be treated as speed claims.

Generated workloads contain 4, 64 or 1,024 procedures, with locals, loops, scalar arguments and short-circuit logic. Benchmarks cover lexing, parsing (including lexing), semantic resolution, LLVM module construction/verification, module construction plus text serialization, and the full source-to-IR pipeline. Backend stages reuse prepared inputs outside timing. `lower_llvm` prepares its LLVM context outside timing; `emit_llvm` includes context creation and serialization. Both call the public lowering API, which constructs a native target inside each timed invocation. They do not measure optimization, object emission, linking or native execution.

Two additional benchmarks lex all local reference sources and all pinned recent upstream sources. Corpus loading and decoding happen before timing. These measure lexical work only; no upstream or reference program executes. Corpus parsing, module resolution and native linking benchmarks must be added as those stages become available.

The separate `vm` benchmark measures actual execution of checked IR at 4, 64 and 1,024 range iterations or record fields. `range_execute_cold` includes interpreter construction; `range_execute_reuse` reuses interpreter storage between calls. `record_copy_execute` initializes a record, copies it, mutates the original, and reads the preserved copy. Fixture construction and IR validation stay outside timing. Preflight checks prove the expected results and that completed frames release their virtual allocations. These cases expose Rust allocation costs of interpreted execution, including snapshots and aggregate copies; they do not measure source `#run` scheduling or generated native runtime.

Divan's allocation profiler wraps the system allocator only in the benchmark executable. Counts distinguish allocation, deallocation and grow operations; do not confuse maximum live bytes with total allocated bytes. Profiling adds timing overhead. These single-thread measurements do not track allocations from unmanaged threads. LLVM allocates through its native allocator, so Rust allocator counters exclude LLVM's internal heap usage. Native heap profiling must be added before making whole-backend allocation claims.

Nested integer ranges have separate `range_lower_llvm` and `range_pipeline` cases at 4, 64 and 1,024 procedures. They exercise reverse traversal, named outer continue/break and verified LLVM construction without changing the original baseline workload. They benchmark compilation, not generated program runtime.

Deferred nested loops have `cleanup_lower_llvm` and `cleanup_pipeline` cases at the same sizes. They include cleanup on named outer exits and track both IR resolution allocations and LLVM construction costs. Original workloads stay unchanged for comparison.

Constant dependency workloads have `constants_resolve` and `constants_pipeline` cases at 4, 64 and 1,024 declarations. They exercise forward dependency worklists, literal evaluation and initialized global storage without changing the earlier generated procedure workload.

Conditional expression workloads have `conditional_lower_llvm` and `conditional_pipeline` cases at 4, 64 and 1,024 procedures. They combine integer and Boolean `ifx` results with nested conditionals and short-circuit control flow, including PHI verification.

Mixed-width workloads have `integer_lower_llvm` and `integer_pipeline` cases at the same sizes. They exercise `u64` arithmetic, checked and intentional narrowing, signed extension, scalar defaults, named argument reordering, and exhaustive Boolean cases. These are separate fixtures; the original comparison workloads remain unchanged.

The `discovery` suite measures in-memory graph loading at 4, 64 and 1,024 sibling files. `module_discovery` discovers unconditional loads; `module_discovery_resume` pauses at a `#run` condition and resumes after selecting its known Boolean result. Input generation stays outside timing. Final file counts are checked. Graph construction/parsing are included; filesystem I/O and VM evaluation of the condition are excluded.

VM `any_box_borrow_fresh_execute` boxes distinct array-element lvalues into canonical `Any` descriptors, passes a slice to a checked procedure, and reads the original payloads through their virtual pointers. Source graph parsing/resolution stay outside timing; VM construction and first descriptor/byte-image initialization are included. Sizes 4 and 64 use default limits. `any_box_borrow_1024_fresh_fuel_32m_execute` measures the same cold request with an explicit benchmark-only 32,000,000 fuel budget, chosen after the frozen diagnostic's first successful execution charged 30,543,926 steps. Each sample constructs a fresh VM and checks the expected sum and two persistent backing allocations. Global VM defaults remain unchanged.

`any_box_borrow_reuse_execute` separately measures sizes 4 and 64 after 40 successful warmup calls. `any_box_borrow_1024_reuse_fuel_32m_execute` measures warmed size 1,024 with the same explicit 32m budget as its cold counterpart. `checked_call_execute` repeatedly calls a scalar procedure using a prepared VM. Its guard expects one persistent implicit context allocation. Canonical runtime `Type` descriptors and default context backing intentionally outlive successful requests; completed frame allocations must still release. The separate `range_execute_cold` case includes VM construction. These suites do not yet isolate deep pointer-projection metadata.

`any_box_borrow_1024_default_fuel_rejection` separately asserts rejection under 1,000,000 fuel and complete rollback. It reports throughput per failed request, rather than per successfully processed array element. Review this explicit resource expectation when changing VM accounting; it is not a Jai language rule.

The failed immutable run `20261002T112757.281590Z` demonstrates why completion guards belong inside timing. All smoke checks passed, including 40 warmed 1,024-element requests at 148,137,004 steps, but later timed reuse exhausted its explicit 160m fuel budget. A separate timed diagnostic also exhausted default fuel for reused size 64. Earlier probes under `20261002T102143.703373Z/diagnostic-budget-probe/` are diagnostics, not valid timed baselines. Do not raise global budgets or report these failures as successful execution.

The pre-retirement diagnostic `20261002T112757.281590Z/diagnostic-fresh-history-smoke/` timed a fresh size-64 interpreter until rejection: 56 requests completed before default fuel exhausted, with 25,629,722 total charged steps and two allocations retained after rollback. Its archived benchmark source preserves that history case. The active reuse benchmark checks successful requests after data tokens stopped retaining retired frame history; keep the old failure evidence separate from the next source snapshot.

The own-code resource probe `any-post-token-probe-20261002T121047Z` records stable repeated Any charges after token retirement: size 64 completed at 129,951 cold steps and 129,644 on the next two requests; size 1,024 completed at 30,582,111 cold steps and 30,581,804 on reuse under 32m fuel. Its default-1m and explicit-2m requests still rejected and rolled back to zero allocations. The probe retains exact linked library hashes and source; it is not a timing baseline.

Every timed VM iteration checks the expected outcome and live virtual allocation count; scalar calls also check their call count. Validation adds small branches to timing without allocating on success. Every VM preflight records fuel, charged steps, calls, expected outcome and persistent allocations in `JAI_BENCH_WORKLOAD` JSON lines, collected into each run's metadata. Successful and resource-rejection measurements remain separately named.

The `unsigned_string_index_cold` and `unsigned_string_index_reuse` cases execute checked source that repeatedly reads a one-byte string through a `u64` index, at 64, 1,024 and 4,096 iterations. Cold samples include VM construction; reused samples follow 40 warmup calls. Both use an explicit benchmark-only 4,000,000 fuel budget and verify the sum and exactly two persistent allocations: implicit context and immutable literal backing. Compiler `unsigned_string_index_resolve` measures resolution of pre-parsed source at 64 and 1,024 index expressions, with a separate successful VM preflight. Extend the `sequence_indices.rs` benchmark modules to compare other source index types or sequence kinds.


Compiler `source_run_resolve` resolves a pre-discovered graph whose entry returns a compile-time range-sum call at 4, 64 and 1,024 iterations. It includes semantic scheduling, checked IR construction, VM execution and constant embedding; parsing/graph construction stay outside timing. A preflight executes the resulting program and checks the sum. This is a successful pure source `#run` case, not effect replay or workspace scheduling.

## How to change it

Shared type cases use 4, 64 and 1,024 graph levels. `type_intern_create` includes registry initialization and new pointer/array/slice/dynamic-array interning; `type_intern_reuse` repeats those lookups in a prepared registry. `nominal_graph_build_freeze` includes nominal reservation, recursive pointer/descriptor definitions, and freeze's value-cycle validation. `type_layout_cold` computes explicit LP64 layouts for nested records in a fresh engine; `type_layout_cached` queries a prewarmed root. Fixture construction and freeze happen outside layout timing. Preflight assertions check canonical IDs, graph cardinality, root size/alignment and field offsets before measurements. These measure shared type infrastructure, not source syntax support or a verified target ABI.

Add a representative, correct workload to `crates/jai-bench/benches/compiler.rs` or a module under `benches/compiler/`, and use existing behavior tests or a meaningful new test for the feature it exercises. `fixtures/mixed_module.rs` owns the shared mixed source and independent checksum; `compiler/whole_module.rs` owns its stage cases, `vm/mixed_runtime.rs` owns Runtime-phase cold/reuse cases, and `compiler/native_runtime.rs` owns native batching, the authored C harness and trusted tool boundary. Extend all stage variants together when changing the mixed fixture, preserve useful small/medium/large sizes, and keep optimization preparation outside object-emission timing. Avoid timing filesystem reads, source generation, fixture preparation or failed compilations inside a successful-stage benchmark. Keep rejection-path measurements separately named.

Run `cargo bench --offline -j1 -p jai-bench --bench compiler --bench vm --bench discovery --locked -- --test` for smoke checks of all three benchmark executables. Add `--skip reference_lex` when the local public source files is absent. After fetching upstream sources, use `--include-ignored` to include the optional upstream case. CI performs smoke checks, without timing gates on a shared runner.

## Configuration

Run `python3 tools/benchmark.py --offline --samples 100 --upstream` using Python 3.11+. On the development Mac, `/opt/homebrew/bin/python3` provides the required Python version; the system Python is too old. It records compiler (including shared types), VM and discovery suites; select one with `--bench compiler`, `--bench vm` or `--bench discovery`. Use `--smoke` to save validation without timing, or `--skip-reference` when the local public source files is absent. Omitting `--upstream` uses only local reference lexing and generated workloads.

Direct invocation of a retained Divan executable needs its hidden `--bench` flag to collect measurements: `executables/vm --bench --sample-count 25 --sample-size 1 --color never`. Without `--bench`, Divan runs test mode and prints only a tree, even when sample flags are supplied. The runner sets `--bench` for timing and `--test` for smoke, and rejects timing output without actual time columns, matching sample counts, measured rows and Rust allocation statistics.

The runner captures an isolated source snapshot, checks that snapshot's locked dependency ages, builds locked benchmark executables from it with one Cargo job, and runs every selected suite in smoke mode before taking measurements. Capturing before the network check prevents concurrent workspace edits during that check from changing the intended build. `--offline` applies to Cargo; the independent dependency-age checker still queries crates.io and fails closed if publication metadata is unavailable. Use `--context-note` to record concurrent builds or other measurement conditions in metadata. Each smoke or measurement suite has a 600-second timeout; change it with `--timeout-seconds`. Keep `LLVM_SYS_221_PREFIX` pointed at the independently installed LLVM 22 prefix. Native batch cases accept `JAI_RS_CLANG`, then `LLVM_SYS_221_PREFIX/bin/clang`, then validated Clang 22 on `PATH`. Their native tool resolver checks against the actual corpus root even when source is built from an isolated snapshot. Original native inputs are never tool, link or execution inputs. Native tool search, injected library and header search variables are scrubbed from the build/run commands. The script disables an inherited compiler wrapper. Target selection follows `--target-dir`, then a nonempty `CARGO_TARGET_DIR`, then pinned offline/locked Cargo metadata. The resolved absolute directory is explicit in the snapshot build command, artifact validation and receipts. This host requires `--target-dir /Volumes/CodexBuilds/targets/jai` on the mounted APFS cache; see [build storage](build-storage.md).

Each `artifacts/benchmarks/<timestamp>/` contains per-suite smoke and timing output, stderr, process resource JSON, combined `results.txt`, Cargo JSON artifact records, dependency-age output, isolated `source/`, compiler-source archive, retained own benchmark `executables/` and format-3 `metadata.json`. Metadata records the selected target directory/source, metadata query when used, explicit build command, sample settings, hardware, load averages, compiler/LLVM versions, selected build environment, source/corpus hashes, executable hashes and exit status. Allocation figures cover the instrumented Rust allocator; native LLVM allocations remain excluded. `JAI_BENCH_CORPUS_ROOT` tells the lexer benchmarks to read the original repository's source corpora; the runner sets and records it. Direct Cargo runs default to their manifest's repository root. The runner sets `JAI_BENCH_NATIVE_ARTIFACTS` to retain freshly generated own C harnesses, objects and executables, hashes only the permitted output names inside that run directory, and rechecks them after all measurements. Its metadata also hashes the validated Clang executable; native replay depends on that exact independent tool and the trusted host linker/runtime. Direct Cargo runs use disposable own temporary output directories.


The runner's provenance, command and resource guards have focused tests: `python3 -m unittest discover -s tools -p 'test_benchmark*.py'`. The resource tests run an own Python child to verify real memory accounting, nonzero failure propagation and timeout cleanup. There are no performance thresholds. Use the same workload, flags, allocator instrumentation and hardware for comparisons, and separate shared-host measurements from controlled regression evidence.

The initial 50-sample shared-host run recorded a 5.07 ms median source-to-IR pipeline for 1,024 generated procedures, 31,784 allocation operations plus 1,081 grows, and about 4.16 MB maximum live allocation. Reference and upstream lexical medians were 137.6 ms and 181.2 ms. Raw measurements are in `artifacts/benchmarks/20261001T221256.105252Z/results.txt`.

A later run after scalar-cast/compound-update work recorded 11.88 ms for the same generated workload, with identical allocation counts. Its lexical medians rose to 305.9 ms and 440.9 ms while other builds/tests shared the host. This demonstrates why these timings cannot establish a regression or improvement without controlled measurement. `artifacts/benchmarks/20261001T222905.259878Z/` also includes a compiler-source archive and corpus fingerprints. Both recorded runs used the earlier handwritten text backend. The LLVM API replacement changes the workload and memory accounting, so those runs are historical baselines rather than performance comparisons for the current backend. These are instrumented baselines, not optimized results or Jai compiler parity.

A 25-sample LLVM API baseline at `artifacts/benchmarks/20261001T231909.958818Z/` records LLVM 22.1.1 and explicit Rust-only allocation scope. For 1,024 procedures, medians were 5.62 ms for module construction/verification, 17.27 ms including serialization, and 22.69 ms for the complete pipeline. The pipeline recorded 58,419 Rust allocation operations plus 1,065 grows and 4.35 MB peak live Rust allocations; native LLVM heap use is excluded. The shared host was active, so these remain descriptive baselines without a performance gate.

[Metadata](../artifacts/benchmarks/20261002T121811.416725Z/metadata.json) and [raw measurements](../artifacts/benchmarks/20261002T121811.416725Z/results.txt) record a valid run of all three suites after data-token retirement. All smoke checks passed, followed by actual Divan measurements of 76 compiler, 25 VM and 6 discovery cases, each with 25 samples and one iteration per sample. Every VM timing checked its outcome and persistent allocation count. The dependency-age check passed for all 40 locked external packages.

The exact 984-file Rust/native-source snapshot is retained in `source/` and `compiler-source.tar.gz`, whose SHA-256 is `a0d42e30757369790224a068f50500bcf5f1804e9184fc707493440d2e42a2d3`. Its input hashes, all 17 output hashes and the three retained executable hashes were verified after measurement. Three live-tree edits were recorded separately; they did not modify the isolated build. Replay the retained own executables to keep the measured implementation fixed.

The host was an Apple M5 Mac17,2 with 10 physical/logical CPUs and 16 GiB RAM, running aarch64 macOS. The build used Rust `1.100.0-nightly (17fd5b8a3 2026-08-28)`, Cargo `1.100.0-nightly`, and independently installed LLVM 22.1.1. It used the default optimized Cargo bench profile, one build job, `RUSTC_WRAPPER=` and `LLVM_SYS_221_PREFIX=/opt/homebrew/opt/llvm`, with no recorded Rust flags or profile overrides. The invocation was `tools/benchmark.py --offline --samples 25 --upstream`; timed executables received `--bench --sample-count 25 --sample-size 1 --color never --include-ignored`. Exact paths, commands and corpus fingerprints are in metadata.

## Dependencies

Divan 0.1.21, selected with the native 14-day Cargo policy, and Inkwell/LLVM 22 for target passes and object emission. Native runtime cases additionally require independently installed Clang 22, the trusted host linker and standard C runtime. Each runner invocation verifies every external package in its captured lockfile before compilation; its dependency-age log records the exact set. Compiler crates remain independent of Divan. See [dependency policy](dependency-policy.md) and [cross-target acceptance](cross-target-acceptance.md) for the separate object, ABI and actual execution evidence boundaries.
