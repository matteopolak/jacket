# C++ vtables

`Bindings_Generator` emits C++ virtual dispatch tables for single-inheritance classes on 64-bit macOS, Linux and MSVC Windows, with x86-64 or arm64 targets. Each generated slot is a `#type (...) #cpp_method` function pointer, which Jai calls like a C function, and its first argument is the instance pointer.

## How it works

`stdlib/internal/developer-tools/generator-record-metadata.jai` builds the table from canonical libclang declarations. It starts from the base's slots, replaces overridden slots using Clang override identity, and appends new methods in declaration order on Itanium targets. MSVC groups new same-name overloads in reverse declaration order. The object points at the first callable slot, after the Itanium ABI offset-to-top and RTTI entries. Omitted methods retain opaque pointer slots so subsequent offsets remain correct.

The printed shape follows the official generator. `Info.vtable` keeps the full slot list (the layout and the tests use it), but a `<Record>_VTable` lists only the slots its record adds, after `using vtable: <Base>_VTable;` when there is a base, so an overriding method is the base's slot and a call dispatches to the override. A record holds its base as `#as using,except(vtable) <base>: Base;` with `#overlay (<base>) vtable: *Record_VTable;`, which converts a derived pointer to a base pointer and lets the base's wrappers (`IUnknownish_release(session)`) accept it. The base is a field only if the record's own fields start at or after the base's size; the Itanium ABI may place them in the base's tail padding, and then the record repeats the base's fields (`gm_can_embed_parent`) and gets its own copy of each inherited wrapper. Only the slots a record adds get wrappers (`<Record>_<method>`) and they follow the table in the output; `print_struct_vtable` writes the table, the wrappers and `vtable(obj)`. Comments on destructor and omitted slots name the original C++ method.

The native target triple and requested module `TARGET_OS` must agree. Scalar and pointer signatures are supported. `generator-vtable-abi.jai` also accepts nonempty trivial records up to 32 bytes with alignment at most eight, recursively containing supported fields at their natural offsets. Packed or omitted instance fields are refused. Union, bitfield, dependent, inherited, polymorphic and nontrivial record values remain refused. Destructors retain two opaque slots on Itanium and one on MSVC; they are never exposed as callable destructor helpers. Extended floating values, variadic methods, multiple inheritance and virtual bases remain rejected. Windows aggregate-return slots have a void return and an explicit result pointer immediately after `this`, including for small records; generated helpers expose that same signature. Itanium aggregate results use the platform C ABI.

## How to change it

Update metadata construction and its tests together. Declaration emission consumes the constructed table; optional helpers call the same slots. Whether the pure virtual methods get `virtual_` foreign declarations is decided in `binding_prints_virtual_function`: only a method a library defines does. Add native C++ fixtures under `stdlib/Bindings_Generator/tests/driven/` and assertions that call the generated slots, rather than checking generation alone.

## Configuration and dependencies

The checker uses `JAIC` for the compiler, `DEVELOPER_TOOLS_LLVM_PREFIX` (or `LLVM_SYS_231_PREFIX`) for the LLVM SDK, and `JACKET_OUTPUT_DIR` for generated artifacts. Use a release `JAIC` on macOS. It requires libclang and the checkout binding helpers. On Windows it uses `llvm-readobj` and `llvm-dlltool` to generate an import archive in scratch from the configured `libclang.dll`. It stages a copy at the ignored private `clang-bindings/clang.lib` path named by the native library declaration; MSVC resolves that path beside the declaration. Build those with `tools/developer_checks/build_generator_platform.py` and `build_developer_bindings.py` first.

Run `PYTHONPATH=tools python3 tools/developer_checks/check_developer_tools.py ManifestChecks.test_check_developer_vtables`. It is part of the developer suite. It checks Linux and MSVC Windows x86-64/arm64 target generation on every host, and actual host C++/Jai dispatch at O0/O2 and in the interpreter with every helper option. The model fixture compares native object size, alignment and field offsets (including a derived record that reuses its base's tail padding), exercises cache growth, and verifies unsupported inheritance/variadic diagnostics. `check_developer_cpp_wrappers` calls the wrappers of a four-level interface chain and a COM-style SDK header on a C++ library, and `check_developer_output_format` compares the generated text for a small header with the expected text. The overload/inheritance/destructor/POD fixture compares model order against Clang’s actual vtable dump, then calls every ordinary slot. Cross-target generation does not exercise the ABI, so run the checker on each target host too.

## Header generation and integration checks

`generator-canonical-construction.jai` collects reopened namespaces across linkage blocks and preserves dependent nested record status. `generator-reference-helpers.jai` resolves enum/constant defaults on demand; value emission accepts typed numeric identifiers. Unused system declarations containing extended `long double`, such as Linux `max_align_t`, are omitted with a diagnostic. Supported omitted system declarations retain their canonical model and counters. Explicit extended types remain refused, while eight-byte `long double` maps to `float64` and `nullptr_t` maps to `*void`. Unresolved direct virtual symbols are omitted without discarding their callable table entries.

The native checker also generates and type-checks a complete header with null, size, numeric and template defaults. It permits only the existing Windows include-discovery warning for this fixture; any other diagnostic fails the check. libclang still finds the SDK headers and the generated output must type-check. CI's Windows native jobs run it on both architectures; the developer manifest covers the Unix hosts. On macOS it prefers the release compiler in the configured cargo target directory. The same checker accepts an explicit `JAIC` path.
