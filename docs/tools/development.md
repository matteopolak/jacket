# Development workflow

The Justfile, the pre-commit hook, formatting, the dependency policy and continuous integration.

## Justfile

The root `Justfile` gives each dev command one name. CI's format and lint steps call the same recipes, so local and CI runs cannot drift. `just --list` shows them. Recipes are thin and take options (`just fmt --check --lang jai a.jai`); the logic lives in `tools/dev/dev.py`, which finds or builds the tools (`jaifmt` is rebuilt when `jaic` or its sources are newer; `jailint` via `cargo build -p jailint`).

| Recipe | Does |
| --- | --- |
| `build` | cargo build of `jaic-cli`, `jai-language-server`, `jailint`, then `target/jaifmt`, then the native pieces a release archive ships (below; `--release`, `--native=false`, `-j`) |
| `fmt` | `jaifmt` on Jai; `cargo fmt` plus `tools/dev/rust_item_spacing.py` on Rust (`--check`, `--lang jai\|rust\|all`, `--staged`, paths) |
| `lint` | `jailint -D warnings` on Jai; `cargo clippy --workspace --all-targets -- -D warnings` on Rust (`--fix`, `--lang`, `--staged`) |
| `check` | `fmt --check`, `lint`, `editor`, `nvim-test --unit` |
| `test` | `cargo nextest run --profile ci` (plus `cargo test --doc`; needs [cargo-nextest](https://nexte.st): `brew install cargo-nextest`) and the `tools/` unittests (`--suite cargo\|tools\|all`, `--crate NAME`, `--partition slice:K/N` for one share, `--expr FILTERSET` to narrow it) |
| `nvim-test`, `editor` | Neovim plugin tests; VS Code generated-file checks (skipped with a note without nvim 0.11 / node 24) |
| `repo-checks [style\|paths\|ci-sources]` | CI's text checks (`tools/ci/check_source_style.py`, `check_repo_paths.py`, `check_ci_sources.py`); names narrow the set. CI, `browser-release.yml` (`ci-sources` only) and the pre-commit hook all call it |
| `hooks` | Sets the relative `core.hooksPath=.githooks` (`dev.py hooks`; `just build` does it too, except in CI) |
| `profile-report PROFILE [--top N ...]` | `tools/profile_report.py`: a samply profile summarized by self and inclusive samples ([profiling](benchmarks.md#profiling)) |
| `bump-version X.Y.Z` | `tools/bump_version.py`, the version step of [releases](releases.md) |
| `fetch-upstreams`, `wasm`, `vscode` | `tools/fetch_upstreams.py`, `tools/browser/build_scripting_wasm.py --release`, `pnpm run <script>` in `editors/vscode` |
| `vscode-try [FOLDER]` | Builds the tools (release; `--debug` for debug) and the extension, then opens VS Code with only that extension, in a throwaway profile whose settings point at the built `jailsp`, `jaic`, `jaifmt` and `stdlib/`. `FOLDER` opens in place; without it, a temporary copy of `examples/` |

The recipes export `PYTHONPATH=<checkout>/tools`, which the Python scripts need to import their helpers; running a script by hand outside `just` takes `PYTHONPATH=tools python3 tools/<folder>/x.py` ([module path](tools-layout.md#module-path)).

### Building from source

`just build` gives a checkout what a release archive has beside `stdlib/`, so `jaic` from `target/` behaves like an installed one:

- `tools/native/build_native_libs.py --missing` builds the third-party libraries the stdlib binds into `target/native-libs/<platform>` (the first run downloads and builds all of them, SDL3 alone takes a few minutes; later runs skip what exists). See [native libraries](native-libs.md).
- `tools/developer_checks/build_generator_platform.py` and `build_developer_bindings.py` build the `Bindings_Generator` helpers (`libgenerator_platform` and the libclang tool) into `stdlib/internal/developer-tools/`, when their C sources are newer than the outputs. The libclang tool builds on macOS and Linux only.

Both need the LLVM SDK the compiler builds against (`LLVM_SYS_231_PREFIX`, see [LLVM setup](llvm-setup.md)). A plain `cargo build` makes only the Rust binaries: `generate_bindings` then fails with "library `generator_platform` was not found", and jaic adds a hint to run `just build` when the library is declared in a checkout's `stdlib/` (`in_source_checkout` in `interp/foreign.rs`). `just build --native=false` skips this step. Before building, `just build` checks for what it needs (`missing_dependencies` in `tools/dev/dev.py`): cargo, LLVM 23.1 through `LLVM_SYS_231_PREFIX` or `llvm-config`, and for the native step a C and C++ compiler, CMake while SDL3 is unbuilt, and libclang's headers while the bindings helper is stale. It lists every missing one with how to install it, then stops.

Rust lints: the root `[workspace.lints]` (inherited by every crate through `[lints] workspace = true`) enables `clippy::all`, `pedantic` (with a short allow-list, each entry commented), `cognitive_complexity`, `too_many_lines`, `undocumented_unsafe_blocks`, `excessive_nesting` and `wildcard_imports` (split files import the names they use from their parent explicitly; `use super::*` is only for test modules). Thresholds live in the root `clippy.toml`: nesting 7, cognitive complexity 40, function length 250 (a ratchet; lower it as functions are split). `std::collections::{HashMap, HashSet, LinkedList}` are banned through `disallowed-types`: use `jaic::fxhash::{HashMap, HashSet}`. Every `unsafe` block needs a `// SAFETY:` comment stating its invariant. `unsafe_code` is `deny` workspace-wide: a module that needs it opts in with a scoped `#[allow(unsafe_code)]`, and `jaic-cli`, `jailint`, `jacket` and `jacket-config` carry `#![forbid(unsafe_code)]`. Flatten or split rather than `#[allow]`; a local `#[expect(.., reason = "..")]` is acceptable only with a real reason. A new crate must add `[lints] workspace = true`. The Jai counterpart is jailint's [`excessive_nesting`](jailint.md#excessive_nesting) rule (off by default).

`--staged` takes files from `tools/dev/staged-files.sh` (also used by the hook); clippy cannot run on single files, so for Rust it only decides whether the workspace is linted.

To add a recipe: give it a doc comment (it becomes the `--list` text) and a `[group(...)]`, keep the body to one command and put logic in `tools/dev/dev.py`. Options use `[arg("name", long)]`; a flag is `[arg("check", long, value="true")]` on a parameter defaulting to `"false"`. Needs just 1.58 (CI pins `just-version`). Variadic `*paths` are joined by spaces, so paths with spaces fail. Windows CI does not call the recipes. `JAI_JOBS` sets the default `--jobs` (3, for a 16 GiB machine).

## Pre-commit hook

`.githooks/pre-commit` is a few lines of `sh` that run `python3 tools/dev/dev.py precommit`; it skips with a warning when `python3` is missing. The checks live in `dev.py` and reuse its helpers (`stale`/`newest`, `rebuild_jaifmt`, `repo_check_failures`, `editor_skip_reason`), so `just fmt`, `just build` and the hook share one copy of each rule. Enable with `just hooks`; skip once with `git commit --no-verify`. The hook exports the staged contents (`git checkout-index`) into a temp directory, so a partly staged file is checked as staged and nothing in the working tree is touched.

`just hooks` (and `just build`) set a *relative* `core.hooksPath=.githooks` in the shared git config and remove any worktree-level override. Git resolves a relative path against each worktree's root, so a linked worktree runs its own tree's hooks and no hook needs to hand over to another checkout. An absolute path into the main checkout (which agent worktrees used to get) is replaced the next time `just hooks` runs.

The staged list is intersected with `git ls-files` for this checkout and drops anything under `.claude/`, so a hook run never lints another agent's worktree (each has its own standard library). `[lint] exclude` in `jacket.toml` repeats `.claude/**` for runs that name a directory.

A new per-system file under `stdlib/internal` (one that imports `windows-api`, `posix-api`, `objc-api`, X11 and the like, or `#assert`s an OS) must be listed in `[lint.portability.platforms]` in `jacket.toml`, or the hook's `platform_leak` check fails on it.

| Staged files | Check |
| --- | --- |
| `*.jai` | `jaifmt --check` on the export; `jailint -D warnings` on the working tree files (it needs the surrounding loaders and modules; a file another program `#load`s is linted through that program) |
| `crates/**/*.rs` | `rustfmt --check --edition 2024` per staged blob (stdin mode, pinned nightly); `tools/dev/rust_item_spacing.py --check` |
| `*.sh`, files with a `sh`/`bash` shebang | `shellcheck` on the export (`tools/dev/staged-files.sh shell` picks the files; CI lints every one: `shell-all`). Skipped with a warning when `shellcheck` is not installed |
| anything | `just repo-checks` (`check_source_style.py`: file length allowlist, banners; `check_repo_paths.py`; `check_ci_sources.py`) on the working tree |
| `Cargo.toml`, `Cargo.lock` | `cargo metadata --locked --offline` for the workspace and `fuzz/`, so a stale lock file fails here, not in CI's `--locked` builds |
| `crates/**`, `editors/vscode/**` | `node scripts/build-grammar.ts --check` and `node scripts/build.ts schemas --check` in `editors/vscode` (needs node 24) |

Tools are found in cargo's target directory (`$CARGO_TARGET_DIR`, else what `cargo metadata` reports from `.cargo/config.toml`, else `target/`), the same one `tools/dev/dev.py` builds into, and are built from *this* checkout, because a shared target directory can hold binaries of another checkout (a deleted worktree's) whose file times look current. `jailint` is `cargo build -p jailint` every time (a no-op when current; cargo links this checkout's binary into `<target>/debug/` either way). `jaifmt` is `<target>/jaifmt`, built with `jaic jaifmt/main.jai -O2 -exe <target>/jaifmt` by the debug `jaic` that `cargo build -p jaic-cli` provides, whenever it is older than `jaic` or its sources, or `<target>/jaifmt.checkout` (written after the build, holding the checkout path) is missing or names another checkout. When cargo is missing or fails, or under `JAI_HOOK_NO_BUILD`, the hook uses what exists (a `jaifmt` recorded as built elsewhere is not used: the hook warns and falls back to `PATH`), then `PATH`. `toolkit.repo.jaifmt_path()` is the single Python definition of that jaifmt location: `dev.py`, `run_tests.py`, the generators and the developer checks all read it. A missing tool prints a warning and skips its check. Clippy runs in the pre-push hook instead. `rustfmt --check` in stdin mode exits 0 on a diff, so any output counts as failure. To add a check, add a `check_*` function in `dev.py` that calls `hook.fail(fix, output)` and call it from `cmd_precommit` with its file filter; keep it fast. A CI check that takes about a second and needs no build belongs here too.

| Variable | Effect |
| --- | --- |
| `JAI_HOOK_SKIP` | space-separated checks to skip: `jaifmt jailint rustfmt spacing shellcheck repo locks editor` |
| `JAI_HOOK_NO_BUILD=1` | never build or rebuild a tool: use what exists |
| `JAI_HOOK_VERBOSE=1` | say which checks run |

Tested by `tools/ci/test_pre_commit_hook.py` (also the `hooks` install and `repo-checks`) on a temporary repository with stand-in tools.

## Pre-push hook

`.githooks/pre-push` runs CI's clippy lint (`--all-targets --locked -- -D warnings`) on the workspace packages whose `.rs` or `Cargo.toml` files differ between the pushed commits and the remote (or `origin/main` for a new branch), via `tools/dev/pre_push_clippy.py`. Clippy is too slow for every commit but catches what CI's `compiler` jobs would reject. It lints the working tree, so it warns about uncommitted Rust changes. Skip once with `git push --no-verify`, or with `JAI_HOOK_SKIP=clippy`. On an arm64 Mac, when `jaic` changed, it also lints the integration tests that hold x86-64-gated code (`#[cfg(target_arch = "x86_64")]`, such as `machine_intrinsics.rs`) with `--target x86_64-apple-darwin`; the host lint never compiles them. It skips that step with a message when `rustup target add x86_64-apple-darwin` has not been run. Enabled by the same `just hooks`.

## Code formatting

Rust uses the pinned nightly `rustfmt` and `rustfmt.toml` (edition 2024, `max_width = 100`, compact items expanded, at most two blank lines). `tools/dev/check_rust_format.py` first checks that every manifest under `crates/` is a workspace member (an unregistered crate would escape formatting), then runs `cargo fmt --all -- --check` and `tools/dev/rust_item_spacing.py --check` (rustfmt does not put blank lines between multi-line items; the script does). Jai uses [jaifmt](jaifmt.md) with the `[format]` section of `jacket.toml`; CI runs `jaifmt --check stdlib tests benchmarks tools jaifmt examples`. A new crate must be added to `members` in the root `Cargo.toml`. Change style options in `rustfmt.toml` and land the reformat as its own commit.

**Format-only commits** (repo-wide `jaifmt` or `cargo fmt`, or a style option change) contain nothing else and use the message `style: format with jaifmt` (or `rustfmt`).

## Output directory

Tools and test scripts write build products, downloads and scratch output under `target/` (ignored; shared with cargo). `playground/` at the repository root is also ignored: a place for local experiments, and where `tools/bench/main.py compare` writes its results (`playground/bench/<timestamp>/`); never commit its contents. `tools/repo_output.py` (`output_dir`, `shared_output_dir`) and `tools/repo_output.mjs` (`outputDir`) are the single helpers; never hard-code a path. `JACKET_OUTPUT_DIR` relocates the whole tree (`jaic` honours it when looking for `native-libs/<platform>`). `shared_output_dir` resolves to the main checkout's directory so worktrees reuse native builds and downloads.

| Directory under the output dir | Contents |
|---|---|
| `native-libs/<platform>`, `native-libs/sources` | `tools/native/build_native_libs.py` output and downloaded sources |
| `sdl3/` | SDL3 source cache, builds, generator, lint and test scratch |
| `thirdparty/` | Slang, JoltPhysics clones and builds |
| `cache/upstream/` | bare clones for `tools/fetch_upstreams.py` |
| `webgpu/<rev>/` | pinned `webgpu.yml` |
| `scripting-runtime/`, `ci-wasm/`, `wasm/`, `browser-release/` | browser bundles |
| `lsp-edits/`, `numerics/`, `extensions-*`, `http-client-*`, `core-public-verification/` | test and verification evidence |

## Dependency policy

Cargo only selects crate versions published at least 14 days ago, direct and transitive. A git dependency must pin a full commit hash that landed upstream at least 14 days ago. `jaic` has one external dependency besides `rayon`, `find-msvc-tools` (Visual Studio and Windows SDK discovery on Windows hosts, [Windows](../native/windows.md)); the other external crates are `serde`/`serde_json` (language server) and `inkwell`/`llvm-sys` (LLVM backend). The same age rule applies to npm packages in `editors/vscode` ([VS Code extension](vscode-extension.md)).

`.cargo/config.toml` enables nightly `min-publish-age` (`registry.global-min-publish-age = "14 days"`, `incompatible-publish-age = "deny"`). Cargo allows young entries already in a lockfile, so `PYTHONPATH=tools python3 tools/ci/check_dependency_age.py [--lockfile PATH]` checks every locked crate against the crates.io API and fails closed on unknown sources, missing metadata, yanked releases and young versions. Git sources are accepted only as `rev = "<40 hex>"` on GitHub, whose committer date is checked via the GitHub API (`GITHUB_TOKEN` authenticates it). It runs before any build in `ci.yml`, `release.yml`, `browser-release.yml` and `fuzz.yml` (for `fuzz/Cargo.lock`). `--cache FILE` (or `$DEPENDENCY_AGE_CACHE`) keeps the registry answers between runs, so only crates missing from it cost the one-second rate-limit pause; an entry is trusted for three days because a release can be yanked later, and a missing or malformed file is just an empty cache. The `.github/actions/dependency-age-cache` action restores it (keyed on the lockfile hashes with a prefix fallback, saved from `main`) in every job that runs the check. Tests: `tools/ci/test_dependency_age.py`.

Checked, not assumed (a dry run with a crate published minutes earlier): Cargo's `min-publish-age` refuses young versions only while resolving (`cargo add`, `cargo update`, `generate-lockfile`); `cargo metadata --locked` and `cargo fetch --locked` accept a young entry already in `Cargo.lock`, so the script above stays. pnpm's `minimumReleaseAge` (`editors/vscode/pnpm-workspace.yaml`) is stricter: a `pnpm install --frozen-lockfile` verifies every lockfile entry against it and fails with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` (checked on pnpm 12.6 and 12.7). So the npm side relies on pnpm for package ages, and `editors/vscode/scripts/check-dependency-age.ts` only does what pnpm cannot: it rejects lockfile entries that are not plain registry packages with an integrity hash, and ages the pnpm release named by `packageManager` itself.

`inkwell` currently comes from git: release 0.10.0 supports LLVM up to 22, while LLVM 23 support (`llvm23-1`) is on its main branch. The root `Cargo.toml` pins an aged commit for `inkwell` and `inkwell_internals`. Once a crates.io release with `llvm23-1` is 14 days old, switch back to `version = "..."` and drop `allowBuiltinFetchGit` in `nix/jaic.nix`. Put shared dependencies in `[workspace.dependencies]`, prefer exact versions, and never weaken the age policy to resolve a conflict.

## Fixing reported bugs

A fix for an issue is done only when a test fails before it and passes after it, on a machine CI has. The steps:

1. **Explain the reported output.** Every line of the reporter's output (diagnostics, error codes, values printed) must follow from the cause you name. If a line doesn't fit, the cause is wrong. For example, issue 15's `pixel_format=0, descriptor unavailable` showed that a format was chosen and then rejected, not that choosing failed.
2. **Reproduce before fixing.** Write the test first and watch it fail. When the bug depends on hardware, a driver or an OS version CI doesn't have, make the code under test take those calls as replaceable procedures and write a stand-in that behaves like the reporter's environment (for example a GL driver whose chosen format has an incomplete descriptor).
3. **Check that the new code ran.** A passing test proves nothing if it never reaches the changed lines. Assert, or print and check, which path the test took.
4. **Run real code before adding a compile error.** A change that rejects code jaic used to accept must pass the sandboxed upstream corpus sweep and smoke checks ([upstream corpus](upstream-corpus.md)) before it lands. Small probes show what the rule rejects; only real projects show what it wrongly rejects.
5. **Ask for confirmation on environment-specific bugs.** When the bug was only seen on hardware or setups we can't run, label the issue `needs confirmation` and leave it open until the reporter confirms the release fixes it.

## Continuous integration

Workflows in `.github/workflows/`:

| Workflow | Runs |
| --- | --- |
| `ci.yml` | pushes to `main`, pull requests, nightly (07:00 UTC) and manual runs: all checks below, including the fuzz crash-input replay |
| `fuzz.yml` | nightly fuzzing and manual runs ([testing](testing.md#fuzzing)) |
| `http-conformance.yml` | only when `stdlib/Extensions/Http/**` or its harness (`tools/stdlib/http_conformance.py`, `http_native.py`, `gen_http_corpus.py`, `http_deviations.json`) changes, and by hand |
| `release.yml` | tags ([releases](releases.md)) |
| `compile-bench.yml`, `browser-release.yml` | manual only ([benchmarks](benchmarks.md), [browser releases](../browser/playground.md)) |

Every action is pinned by full commit SHA with a version comment. `.github/dependabot.yml` opens one grouped weekly PR for the `github-actions` ecosystem (workflows and `.github/actions/*`); cargo and npm are left out on purpose, as they follow their own age policies. Review a bump like any other CI change.

Shared setup lives in composite actions: `.github/actions/setup-unix` (pinned nightly Rust, Python, LLVM 23, Linux native libraries), `apt-cache` (the weekly Ubuntu package cache that `setup-unix` and the SDL3 job share), `setup-windows`, `windows-provider`, `rust-cache` and `native-libs-cache` (see [Caches and shards](#caches-and-shards)). `tools/native/ci_native_deps.sh {developer|clipboard|full}` builds the native helper libraries the jobs link, before any test runs. `just test --suite cargo` builds the missing pinned libraries itself (`build_native_libs.py --missing`) before nextest, so the native tests do not depend on running the script by hand.

`ci.yml` starts with a `changes` job that runs `tools/ci/ci_changes.py`, which diffs the pushed range (or PR base; anything undiffable runs everything) and emits one `jobs` output, a JSON list of the job ids that should run (`JOBS` in the script maps each id to its path area; `ci.yml` gates every job on `contains(fromJSON(needs.changes.outputs.jobs), '<id>')`, and a test keeps the two in step). The areas are: `sdl3`, `clipboard-linux`, `nix`, `shell` (`shellcheck`: every `*.sh` and `.githooks/`), packaging (`install-sh`, `install-ps1`, `homebrew`) and the `windows-*` jobs, plus `code`, which is false when only prose changed (see [Caches and shards](#caches-and-shards)). To gate a job on more paths, add a pattern to `AREAS` in that script (tests: `tools/ci/test_ci_changes.py`). Editing `ci.yml` or `.github/actions/` runs every area except `sdl3`, which runs only for `stdlib/Extensions/SDL3/` and its own tooling (`tools/bindings/*sdl*.py`, `tools/native/sdl3/`); the release workflow still builds and tests SDL3.

**Tiers.** `ci_changes.py` also picks the tier. Pushes and pull requests run the fast tier, which aims to finish in ten minutes; the nightly run and manual runs (`gh workflow run ci.yml`, or `-f tier=fast` for the fast set) run the full tier. It writes `full=true|false` and the matrices of `test` (`test_matrix`) and `stdlib-runtime` (`stdlib_matrix`), so the legs of both live in Python, where `tools/ci/test_ci_changes.py` checks that each shard set is complete, that the fast tier stays within the five macOS jobs and that the full tier covers every platform. Other jobs test `needs.changes.outputs.full == 'true'`. The fast tier runs platform-neutral work once, on Linux x86-64, spreads the long suites over more jobs, and leaves to the full tier: Linux arm64 and macOS Intel, the `-O2` stdlib reruns, sanitizers at `-O2`, the codegen-units run, macOS `tooling`, macOS and arm64 `upstream-smoke`, and on macOS the tests of the crates that do not depend on the host (only `jaic-cli`, `jaic-llvm`, `jaic` and `jacket` run there). To move a check between tiers, edit `test_matrix`/`stdlib_matrix` or the job's `full` condition.

Jobs that run for every code change (`code=true`):

- `scripting-wasm` (ubuntu): builds the browser engine and runs `tools/browser/check_scripting_wasm.mjs`, `check_jaifmt_wasm.mjs engine`, `check_playground_stdlib.mjs` (every `tests/compiler/regressions` program in the browser engine) and `test_webgpu_host.mjs`, then differential testing `interp,wasm` with an LLVM-free `jaic`.
- `test` (Linux x86-64 and macOS arm64; Linux arm64 and macOS Intel in the full tier): dependency-age and `tools/ci/check_ci_sources.py` (literal `include_str!` inputs must exist in the checkout) and `tools/ci/check_repo_paths.py` (repo paths named in `docs/` and in tool and config headers must exist; generated paths are listed in `GENERATED`, user-project examples in `ALLOW`) checks, and `tools/ci/check_source_style.py` (a Rust file over 1,200 lines fails unless it is in the shrink-only `ALLOWED_LONG` list with its current line count, which it may not exceed; Rust and Python files may not carry banner comments like `// ------`), `just fmt --check --lang rust`, `just lint --lang rust`, `just test --suite cargo` (nextest's `ci` profile in `.config/nextest.toml`, which holds the list of tests left out because they need the separately supplied reference sources or run in their own step; add to its `default-filter` to skip another; `--ignore-default-filter` runs them), the Python tool tests (`python3 tools/run_tests.py`), the Seatbelt sandbox tests (`test_sandbox.py`, `test_upstream_sandbox.py`: they skip off macOS, so the first macOS Rust shard runs just those two files), `just fmt --check --lang jai`, `just lint --lang jai --release` (an optimized jailint), the same lint with `--os windows` and `--os macos` on Linux x86-64 (each target's modules, which the host lint cannot compile), a `JACKET_TEST_CODEGEN_UNITS=4` rerun of the native tests, differential testing, the wasm target (`jaifmt.wasm` against native, `interp,wasm-native`), and the [stdlib target](testing.md#stdlib-target-check) and [Objective-C selector](testing.md#objective-c-selector-check) checks. Each check runs even when an earlier one failed, so one run reports every failure.
  - **Parts.** Each leg has a `part`, which picks its steps, and a `shard`: `rust` runs one nextest slice (`dev.py test --partition slice:K/N`; doctests in the first) and, in the first slice, the Rust format and clippy; `targets` runs one share of the stdlib target checks (`JACKET_STDLIB_TARGETS_PART=K/N`) and, in the first, the Objective-C selectors; `split` the codegen-units run; `jai` the Jai format check, policy tests and generator checks; `lint` the host Jai lint; `portability` the portability lint (`-D platform_leak`); `lint-windows` and `lint-macos` the other targets' lint; `diff` backend agreement and the wasm target. The platform-neutral text checks (dependency age, `check_ci_sources`, `check_repo_paths`, `check_source_style`, `check_diagnostics_covered`, and the generated bindings and sources checks) run only in `compiler (ubuntu-24.04, jai)`. Each `rust` leg uploads its JUnit (`rust-test-durations-*`), with per-test times for rebalancing. Work that does not depend on the host runs on Linux x64 only: the `jai` leg (policy tests, Jai format check), the WebAssembly target tests (the other hosts' `rust` legs pass `not test(wasm_target)`), the wasm modes of `stdlib_runtime.py` and the wasm runs of `jacket test`. The codegen-units-4 `split` leg runs on Linux arm64 only. `jacket test` over the `[test] paths` modules is divided by `--partition hash:K/N`: over a platform's `tooling K of N` legs, or on its `suites` leg when it has none (Windows: over the stdlib shards). The `-O2` sanitizer sweep runs the modules listed in `tests/compiler/optimized-modules.txt` rather than every module.
- `vscode-extension`, `neovim-plugin`: see [VS Code extension](vscode-extension.md), [Neovim plugin](neovim-plugin.md).
- `stdlib-runtime`: every [stdlib runtime test](testing.md#stdlib-runtime-tests) (`--strict`, Xvfb and Mesa on Linux), in `K/N` legs with the modes of the matrix (fast: Linux x86-64 in three, all modes; macOS arm64 in two, interpreter and native; full: two per platform, all modes plus `-O2`). A `suites` leg runs the producer suites but `bindings` and `tooling` (`check_stdlib_suites.py --suite ... --jobs 2`), `jacket test` and the headless and window WebGPU tests; `bindings` and `tooling`, the longest suites, have legs of their own (on macOS only in the full tier); `tooling` runs in `TOOLING_PARTS` legs (`--tooling-part K/N`: every N-th test of `tools/developer_checks/check_developer_tools.py` from the K-th). `stdlib-coverage` reports the interpreter reachability of all shards together (informational; full tier only).
- `upstream-smoke`: builds and runs pinned third-party projects ([upstream corpus](upstream-corpus.md#smoke-tests)).
- `sanitizers` (Linux x86-64 in two shards, macOS arm64): `tools/differential/jaic_sweep.py --sanitize address,undefined corpus modules regressions` at `-O0` (three Linux shards in the fast tier), and at `-O2` in the full tier (two Linux shards) ([sanitizers](../native/sanitizers.md)).

`docs` (rule coverage, `tools/dev/check_rule_coverage.py`) runs for every change, docs-only ones included.

**macOS runners.** GitHub runs only five macOS jobs at a time per account, across all workflows, so the fast tier has exactly five: two `rust` slices of `test` and three `stdlib-runtime` legs, all on arm64. The macOS leg of `sanitizers` joins on pushes only when a path of the `sanitizers-macos` area in `tools/ci/ci_changes.py` changes (code generation, the driver, the sweep, native tooling), and then queues. `determinism.yml` runs Linux nightly and macOS only in its Sunday run, after the other nightly jobs. The macOS Intel legs and the macOS entries of `sdl3`, `nix`, `install-sh`, `homebrew`, `upstream-smoke` and `http-conformance.yml` only run in the full tier. Run that before a release.

Path-gated jobs: `sdl3` (native SDL3 artifacts), `clipboard-linux` (X11 clipboard on Xvfb), `nix` (flake check and build; [releases](releases.md#nix)), the packaging jobs (install scripts and Homebrew formula on macOS, Linux, Windows), and the Windows jobs: `windows-cross` (MinGW cross-builds corpus and stdlib programs, x64 and arm64, a third per job with `windows_cross.py build --shard K/3`), `windows-run-cross` (runs each third on Windows), `windows-native` (builds `jaic` against the official LLVM and runs the platform checks, `cargo test --test native` and the WebGPU tests on D3D12 WARP, in a `programs` and a `graphics` job per CPU), `windows-stdlib` (the stdlib runtime tests; `windows_stdlib_matrix` in `ci_changes.py`: fast, five x64 shards without `-O2`; full, two per CPU with `-O2`) and `windows-smoke` (third-party projects). Windows arm64 runs only in the full tier (`windows_cpus` in `ci_changes.py`): the fast tier is bound by GitHub's limit of 20 jobs at once per account, so its total job time, not its longest job, decides how long it takes. The Windows jobs (x64 and arm64) install Mesa's llvmpipe `opengl32.dll` from a pinned, checksum-verified mmozeiko/build-mesa release (`tools/ci/install_ci_mesa_windows.sh CPU DIR`) because runners only have GDI OpenGL 1.1. See [Windows](../native/windows.md).

The full corpus sweep with the `upstream` set is not in CI (the corpus is fetched, not committed); CI fetches only what the smoke checks use.

**Concurrency.** A push cancels that branch's older `ci.yml` run. On `main` every push has its own group so the light jobs finish for each commit; heavy jobs (`stdlib-runtime`, `upstream-smoke`, sanitizers, the Windows jobs, the Intel leg) have job-level `concurrency` keyed by job, ref, platform and shard, so only the newest `main` commit runs them to the end. Add or remove that block to change which jobs are heavy. Nightly fuzz runs never cancel.

**To change it:** edit the workflows. Keep each check's step id paired with the `steps.<id>.outcome` test in the job's final enforcement step, or failures are silently ignored. Pin third-party actions by commit SHA and keep `permissions: contents: read`. A `test_*` Python file under `tools/` is picked up by the Python test step; Node tests must be added to the relevant job by hand. Runners: `macos-15`, `macos-15-intel`, `ubuntu-24.04`, `ubuntu-24.04-arm`, `windows-2025`, `windows-11-arm`; 30 minute timeouts (45 for sanitizers and each stdlib runtime shard); `CARGO_INCREMENTAL=0`; toolchain `nightly-2026-08-29`; Python 3.14; node 24.

### Caches and shards

The time goes into running tests, not into building the tools: a job's own `cargo build` of `jaic` takes under a minute, so each job builds what it uses rather than downloading it from a build job it would have to wait for (`tools/differential/jaic_sweep.py` also refuses a `jaic` older than the checkout's sources). What is cached:

| Cache | Where | Key | Saved |
| --- | --- | --- | --- |
| Cargo registry and dependency builds | `.github/actions/rust-cache` (`Swatinem/rust-cache`), used by `setup-unix`, `setup-windows` and `scripting-wasm` | job, OS, toolchain, `Cargo.lock`, Cargo env vars (rust-cache's own) | from `main` only |
| `target/native-libs` ([native libraries](native-libs.md)) | `.github/actions/native-libs-cache` | OS, CPU, `LLVM_VERSION`, and the hash of `tools/native/native-libs.json`, `tools/native/**` and the build scripts | from `main`, when the job succeeds |
| `target/window-native`, `target/production-bindings/native`, `target/clipboard-native`, `target/native-stamps` | the same action with `helpers: 'true'` (`stdlib-runtime`, `sanitizers`), as a separate `-helpers` entry | the key above plus the hash of the helpers' sources | from `main`, when the job succeeds |
| `target/cache/upstream` (blobless mirrors of the pinned third-party projects) | `actions/cache` in `upstream-smoke` and `windows-smoke` | OS, CPU and the hash of `corpus/upstreams.json` and `tools/upstream-cases.json`, falling back to the newest older entry | from `main` |

rust-cache treats every directory under `target/` as cargo's: it saves them trimmed to their cargo parts and, on a partial key match, trims them before restoring. The tools keep working state there (`target/cache/upstream`, `target/sdl3`...), so the action moves the job's non-cargo entries aside, restores, deletes the non-cargo entries the cache brought back and moves the job's own back (a cargo entry is a directory with `.fingerprint`, directly or under a target triple). Keep tool output out of `target/<profile>/`, which is cached.

The native libraries are the cache that matters (SDL3 alone takes about three minutes to build). The jobs build them with `tools/native/build_native_libs.py --missing`, which builds only the libraries absent from `target/native-libs/<platform>`, so a restored directory costs nothing and a new key (any change to the manifest or the scripts) rebuilds from scratch. There are no `restore-keys` for that reason: an older set would be kept as it is. A build input outside the key (a new script the build imports) must be added to the `hashFiles` list in the action. Linux and macOS arm64 install LLVM from apt and Homebrew, which are fast and not cached; the `sdl3` job builds SDL3 itself on purpose and has no cache. The helper libraries of `ci_native_deps.sh full` (window, production bindings, clipboard provider) go through `stamped` in that script: each keeps a stamp (hash of its tracked input files, OS, compiler, LLVM) in `target/native-stamps/` and is rebuilt unless the restored stamp and output match, so a stale cache costs time but never correctness. A new helper joins by wrapping its build in `stamped NAME OUTPUT_DIR INPUTS... -- COMMAND` and adding its output directory to the `helpers` paths of the action. The Debug/developer helpers write into `stdlib/internal/developer-tools` and the audio build runs a device test, so they always run.

Long sweeps are split with `--shard K/N` (`tools/stdlib/stdlib_runtime.py` and `tools/differential/jaic_sweep.py`): shard K runs every N-th selected case from the K-th, so a module's neighbouring tests land in different shards and the split is the same on every run. To change the count, edit `shards(N)` in `test_matrix`/`stdlib_matrix` or the job's matrix. The matrix `shard` values are passed to `--shard` as written (`'1/2'`).

A push or pull request that only changes prose (`docs/**`, top-level `*.md`, `.github/*.md`) sets `code=false` and skips every build and test job; `docs` still runs. Docs that a test or generator reads (`docs/specs/**`, `docs/tools/jailint.md`) count as code: add others to `READ_BY_TESTS` in `tools/ci/ci_changes.py`. Markdown elsewhere (test fixtures) is code.

`release.yml` has one concurrency group per tag (a tag push and a dispatch for that tag share it) that never cancels: a second run waits for the first instead of publishing alongside it. GitHub keeps one waiting run per group, so a third replaces the waiting one.

## CI plumbing scripts

Workflow YAML calls scripts under `tools/ci/` instead of carrying shell logic, so each piece is testable and shared:

- `.github/pins.json` is the one place for tool versions the workflows download (node, python, just, ruff, LLVM, llvm-mingw, mesa, nvim, with SHA-256s). `PYTHONPATH=tools python3 tools/ci/pins.py check` fails when a workflow disagrees; `pins.py sync` rewrites them.
- `published_release.py` is the "is this version published yet" check used by `install-sh`, `install-ps1` and `homebrew` (`--formula` for the formula).
- `enter_vs_dev_shell.ps1` (dot-source it) loads the Visual Studio developer environment on Windows jobs.
- `install_pinned.py <tool>` is the one installer for pinned downloads, reading `pins.json`: `nextest`, `llvm-cov` and `cargo-mutants` download the prebuilt archive for this platform, compare its SHA-256 with the pin and only then unpack it into `$CARGO_HOME/bin` (a platform without a pinned checksum fails and names the `cargo install --locked` command); `rust [--component NAME] [--target TRIPLE]` installs the channel from `rust-toolchain.toml`; `llvm-release ARCHIVE` downloads and unpacks the official LLVM release into `$RUNNER_TEMP/llvm` and exports `LLVM_SYS_231_PREFIX`. To add a prebuilt tool, add its `Prebuilt` entry (URL template, per-platform target and checksum key) and the pins; `test_install_pinned.py` runs it against stub archives. `test_install_sh.py` / `test_install_ps1.ps1` do the same for the user installers.
- Step bodies longer than about ten lines live in scripts here, not in the workflow YAML, so they can be linted (`shellcheck` runs over `tools/ci/*.sh`), read and run by hand. The workflow keeps the matrix, `if:` and `needs:`; a `${{ matrix.* }}` value the script needs reaches it as an environment variable set on the step (`NAME`, `LLVM`, `SUITES`, `WASM`). The scripts: `release_meta.sh`, `macos_static_zstd.sh`, `package_release.sh`, `smoke_packaged_compiler.sh`, `publish_release.sh`, `open_vsx_publish.sh`, `homebrew_tap_push.sh` and `nvim_mirror_push.sh` for `release.yml`; `stdlib_jacket_test.sh`, `stdlib_producer_suites.sh`, `nix_smoke.sh`, `install_sh_release_archive.sh`, `install_sh_upgrade.sh` and `simp_game_without_clang.sh` for `ci.yml`. Each starts with a comment naming the variables it reads. A script keeps the shell flags its step had (`set -e`, or `set -eo pipefail` where the job's default shell was set to `bash`).
- `apt_lib.sh` / `apt_install.sh` select the CI package repositories and provide bounded retries; `check_formula.sh <formula> <tap> audit|install` runs the brew checks.

### Ubuntu CI package sources

`apt_configure` in `tools/ci/apt_lib.sh` copies the runner’s Ubuntu `ubuntu.sources` file (or legacy `sources.list`) into `/etc/apt/jai-ci-sources.list.d`. A job-local APT configuration selects that directory and keeps request timeouts, retries and signature verification. Unrelated vendor feeds preinstalled on hosted images are left intact but are not dependencies of our package updates. Missing Ubuntu sources and failed updates to selected repositories remain fatal. When `JAI_APT_ARCHIVES` is set, apt downloads into and installs from that directory; `.github/actions/apt-cache` (used by `setup-unix` and the SDL3 job) sets it and caches the directory weekly per CPU and package set (saved from main), so Linux jobs rarely touch the runners' sometimes-crawling Ubuntu mirror.

`install_ci_llvm_linux.sh` adds its fingerprint-checked, signed LLVM source to the same directory. To add a required repository, register it there before updating; do not re-enable all inherited feeds or ignore update errors. Both helpers configure the selection, so later direct `apt-get` calls in a job use it too. See APT’s [source file configuration](https://manpages.debian.org/bookworm/apt/apt-get.8.en.html#FILES).

The source selection needs Ubuntu’s package-source files, `sudo`, `install`, and APT. Production callers pass `/etc/apt` explicitly; package arguments belong to `apt_get install`, not `apt_configure`. Regression tests in `tools/ci/test_apt_lib.py` use a temporary filesystem to check vendor isolation, legacy sources, repeated setup retaining LLVM, and required-update failure propagation. Shared APT setup changes also select the Windows cross-build jobs in `ci_changes.py`.
