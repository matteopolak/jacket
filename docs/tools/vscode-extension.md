# VS Code extension

## What it is

`editors/vscode/` is the Visual Studio Code extension for Jai: a TextMate grammar, language configuration and snippets, a client for [`jailsp`](../compiler/language-server.md) (which also carries [jailint](jailint.md)'s findings and fixes), [`jaifmt`](jaifmt.md) as the document formatter, *Run/Build/Check File* commands, and a downloader for the compiler release named in its checksum manifest. The extension package version and compiler version are independent so a checksum repin can ship without changing the compiler version. Its ID is `matteopolak.jacket` (publisher `matteopolak`, name `jacket`; it was `matteopolak.jai` up to 0.4.1 and `matteopolak.jai-toolchain` after, see [The old extension IDs](#the-old-extension-ids)), under the repository's AGPL-3.0-or-later license. It ships as a `.vsix` attached to GitHub releases and is published to the Marketplace and Open VSX once their tokens are configured ([Publishing](#publishing)).

## How it works

```
src/extension.ts        activation, the LanguageClient, restart, jailint.toml sync, the formatter
src/discovery.ts        finding jailsp, jaic and jaifmt (pure; unit-tested)
src/toolchain.ts        release archive per platform, checksums, download, versioned install (pure)
src/toolchainManager.ts asking before a download, progress, remembered answers (VS Code side)
src/jaifmt.ts           jaifmt.toml lookup, ignore globs, the minimal edit, running jaifmt --stdin
src/commands.ts         Run/Build/Check File as VS Code tasks
src/expansion.ts        jai.showExpansion / jai.showPolymorphs results, jai-expansion: documents
scripts/build-grammar.ts   writes syntaxes/jai.tmLanguage.json
scripts/build-schemas.ts   writes schemas/jailint.schema.json (from jailint's RULES) and jaifmt.schema.json
```

**Highlighting.** `syntaxes/jai.tmLanguage.json` is generated by `scripts/build-grammar.ts`, where identifier, keyword and directive lists are spelled once. It is the fast baseline; `jailsp`'s semantic tokens (`semanticTokensProvider`, full documents) refine it once the server answers. The grammar was written from the compiler's lexer and parser (`crates/jaic/src/lexer.rs`, `parser/`) and this repository's code, not from any other editor's files. Notable rules:

- Here-strings: `#string TAG` (with `,cr` or `,\%` flags) up to a line whose first word is `TAG`, using a back-reference in the end pattern. The rest of the opening line is not code, as in the lexer. When `TAG` names a language (`#string WGSL`), the body is highlighted as that language ([Embedded languages](#embedded-languages)).
- Block comments nest. Strings may span lines.
- Doc comments: a run of whole-line `//` comments is wrapped in `meta.comment-run.jai` (no styling of its own), and `syntaxes/jai-doc-comments.tmLanguage.json` injects Markdown styling (`markup.bold`, `markup.italic`, `markup.inline.raw`, `markup.heading`, list bullets, `markup.underline.link`) and Jai highlighting of fenced code into comments. Markers stay visible. See [doc comments](../compiler/doc-comments.md). The injection is hand-written; its tests are in `test/grammar/doc-comments.jai`.
- Numbers: `0x`, `0b`, `0h` (a float by bit pattern), `_` separators, `1.`, `.5` and exponents, but not the `1` of `1..2` or `1.foo`.
- Declarations: names before `::`, `:=` or `:` (several, as in `a, b := f();`), procedures (`name :: (...)` followed by `->`, `{`, a directive, a note or the end of the line; `N :: (A + B) * 2;` stays a constant), types (`:: struct`, `enum`, `union`, `#type`), the type after a declaration's `:` and after `->` (not a named result), and `for x, i: xs` loop variables, so `xs` is not taken for a type.
- `$T` is `entity.name.type.parameter`, `$$x` `variable.parameter.baked`; `cast`/`xx` with their `,no_check`/`,trunc` flags; `it`/`it_index`; `context`; builtin types and `size_of`/`type_info`-style builtins.

### Embedded languages

A here-string's terminator doubles as a language hint. When it names a language from the table below (compared ignoring case), the body is highlighted as that language, with its comments, brackets and snippets; any other terminator (`END`, `DONE`, `HERE`) stays a plain string. There is no other syntax for it: the code compiles the same either way.

```jai
GPU_SCENE :: #string WGSL
@vertex fn vs(@builtin(vertex_index) i: u32) -> @builtin(position) vec4f { ... }
WGSL
```

| Terminator | Language | Grammar |
| --- | --- | --- |
| `WGSL` | WGSL | `source.wgsl` from a WGSL extension if installed, else the bundled `syntaxes/wgsl.tmLanguage.json` |
| `GLSL`, `VERT`, `FRAG`, `COMP`, `GEOM`, `TESC`, `TESE` | GLSL | `source.glsl` (a GLSL extension) |
| `HLSL` | HLSL | built in |
| `MSL`, `METAL` | Metal | `source.metal` (a Metal extension) |
| `SQL`, `JSON`, `HTML`, `CSS`, `XML`, `LUA` | as named | built in |
| `JS`, `JAVASCRIPT` / `TS`, `TYPESCRIPT` | JavaScript / TypeScript | built in |
| `PY`, `PYTHON` | Python | built in |
| `SH`, `BASH`, `SHELL` | shell script | built in |
| `C` / `CPP` / `OBJC` | C / C++ / Objective-C | built in |
| `RS`, `RUST` | Rust | built in |
| `YAML`, `YML` | YAML | built in |
| `TOML` | TOML | `source.toml` (Even Better TOML) if installed, else the bundled TOML grammar |
| `MD`, `MARKDOWN` | Markdown | built in |
| `JAI` | Jai (code for `#insert`, metaprogram sources) | this grammar |

How it is built: one rule per language in front of the plain here-string rule. Its `begin` is a lookahead that captures the tag (for the `end` back-reference, `^[ \t]*TAG` not followed by an identifier character, so an indented terminator works as in the lexer); inside it, a `begin`/`while` rule takes the header and continues *while* a line does not start with the tag, with `contentName: meta.embedded.block.<name>` and `include`s of the language's grammars. The `while` matters: an embedded construct left open (an unclosed `/*` in the shader) is cut off at the terminator instead of swallowing the rest of the file. `package.json`'s `embeddedLanguages` maps each `meta.embedded.block.<name>` to its VS Code language ID, which is what gives the body that language's comment toggling, bracket pairs and auto-closing. The extension registers a `wgsl` language (no file extensions, `wgsl-language-configuration.json`) so WGSL bodies get those without a WGSL extension.

When none of a language's grammars is installed (GLSL without a GLSL extension), vscode-textmate drops a rule whose includes all resolve to nothing, so the here-string falls back to the plain string rule rather than an uncoloured body. Where two grammars are listed (WGSL, TOML), both apply and the first wins where they match at the same place; the bundled ones are small (comments, keywords, types, attributes, numbers, calls) and only fill in.

jailsp's semantic tokens skip a here-string with a known tag and keep marking the others as `string` (`crates/jai-language-server/src/here_string.rs`).

The playground's editor reads the same tags for the languages it supports (WGSL and nested Jai); see the portfolio's `src/lib/jai/embedded-languages.ts`.

The extension also maps jailsp's non-standard `formatSpecifier` token type (format-string `%`s) to a TextMate scope so themes colour it.

**Language client.** `vscode-languageclient` starts `jailsp` over stdio for `file:` Jai documents (unsaved and virtual documents have no path the compiler could load). Its stdlib comes from `JAIC_STDLIB` (the extension sets it from `jai.stdlib.path`; otherwise the `stdlib/` next to the executable), the project's entry files and module folders from the nearest `jai.toml` (else inferred, see [project settings](../compiler/language-server.md#project-settings-jaitoml)), and lint levels from the nearest `jailint.toml`. Editor settings for jailsp (`jai.completion.autoImport`) go as `initializationOptions` (`serverSettings()`), and `synchronize.configurationSection: "jai"` sends the `jai` section with `workspace/didChangeConfiguration` when it changes, so no restart is needed. A file watcher on `**/{*.jai,jai.toml}` (`synchronize.fileEvents`) sends `workspace/didChangeWatchedFiles`, which keeps jailsp's auto-import index of the project's files current. There is no target-OS option; `#if OS == ...` code is analysed for the host. The client's middleware handles the two server commands: `jai.showExpansion` opens the returned code beside the editor as a read-only `jai-expansion:` document (a `TextDocumentContentProvider` that asks `jai/source` again, so it follows edits), and `jai.showPolymorphs` lists instances in a quick pick.

**Binary discovery** (`findServer`, `findCompiler`, `findFormatter`):

| Tool | Order |
| --- | --- |
| `jailsp` | `jai.server.path`, `jailsp` on `PATH`, next to `jai.compiler.path` or the `jaic` on `PATH`, the downloaded toolchain |
| `jaic` | `jai.compiler.path`, `jaic` on `PATH`, the downloaded toolchain |
| `jaifmt` | `jai.formatter.path`, `jaifmt` on `PATH`, next to `jaic`, next to `jailsp`, the downloaded toolchain |

A configured path that does not exist is an error naming the setting, never a silent fallback. Settings accept `~` and `${env:NAME}`.

**Toolchain download.** When no `jailsp` is configured or found, the extension offers the compiler version in `toolchain-checksums.json` (which defaults to the extension package version for a development build without a pin):

1. `jai.toolchain.autoDownload` decides: `prompt` (the default) asks *"Download jaic X from github.com/matteopolak/jacket?"* with **Download**, **Cancel** and **Don't Ask Again** (which sets the setting to `never`). Cancel is remembered for that version (`globalState`), so the question comes back only for the next version; the warning that jailsp is missing still offers *Download Toolchain*. `always` downloads without asking, `never` only shows how to install by hand. Nothing is downloaded silently by default.
2. The archive comes from `assetFor` in `toolchain.ts`: `RELEASE_ASSETS` maps `${process.platform}-${process.arch}` to `jacket-<platform>.tar.gz` (`.zip` on Windows). Other platforms have no archive and get a message pointing at building from source or setting `jai.server.path`.
3. The download (`fetch`, with progress and a Cancel button) is checked against `toolchain-checksums.json`, which records the compiler version and SHA-256 of each archive pinned into the `.vsix`. A mismatch is rejected. A development build without matching pins falls back to the release's `SHA256SUMS` and says so in the *Jai* output channel.
4. It is unpacked with the system `tar` (bsdtar, which also reads `.zip`; `%SystemRoot%\System32\tar.exe` on Windows 10 and later) into a staging folder, the four executables are checked and made executable, and the folder is renamed to `<globalStorage>/toolchain/<compiler-version>/`. The archive layout is kept (`jacket-<platform>/jaic`, `jailsp`, `jailint`, `jaifmt`, `stdlib/`). Its installed marker records the verified archive hash; a later editor release that pins changed bytes for the same compiler version treats the cached folder as stale and replaces it after verification.
5. Older version folders and interrupted downloads are deleted only after the new version is installed. Until the user accepts an upgrade, the older download keeps working.

Offline, the request fails with *could not reach github.com (ENOTFOUND)* and a Retry button; nothing is half-installed. *Jai: Download Toolchain* downloads on demand. Paths from settings and `PATH` still win over a download; the command says so when that is the case.

**Refactorings, call hierarchy, expand selection.** These are plain jailsp capabilities, so the language client wires them up with no extension code: the light-bulb menu offers the `refactor.*` actions ([list](../compiler/language-server-refactorings.md)), *Show Call Hierarchy* and *Expand Selection* use `callHierarchyProvider` and `selectionRangeProvider`. The e2e suite covers each through VS Code's own commands (`vscode.executeCodeActionProvider`, `vscode.prepareCallHierarchy`, `vscode.executeSelectionRangeProvider`) on `test/e2e/fixture/refactor.jai`.

**Linting.** jailint runs inside jailsp, so its findings are ordinary diagnostics (source `jailint`, the rule as `code`, linked to its docs) with quick fixes, and `source.fixAll.jailint` works with `editor.codeActionsOnSave`. jailsp also reads an *open* `jailint.toml` (and `jai.toml`): the extension sends `didOpen`/`didChange`/`didClose` for files with those names by hand (`SETTINGS_FILES`), so unsaved edits apply at once without adding TOML to the client's document selector (which would send it every Jai request). `jaifmt.toml`, `jailint.toml` and `jai.toml` open as TOML with a small bundled grammar; `contributes.tomlValidation` attaches `schemas/*.schema.json` for TOML extensions that support it (Even Better TOML).

**Formatting.** jailsp has no `textDocument/formatting`, so the extension registers a formatting provider that runs `jaifmt --stdin` with the document's folder as working directory (jaifmt finds the `jaifmt.toml` there or above). Before that it reads the nearest `jaifmt.toml` and skips files its `ignore` globs match, since `--stdin` does not apply them. On success it returns one edit covering only the changed span (common prefix and suffix kept, so the cursor and folds outside it stay put); on failure (unbalanced brackets, text that does not lex) it leaves the text alone and shows jaifmt's message in the status bar and the output channel. `editor.formatOnSave` works through VS Code's normal path; `[jai]` defaults the formatter to this extension.

**Commands.** *Run File*, *Build File* and *Check File* save the file and run `jaic <file> [-interp|-check] <jai.run.arguments>` as a task (*Build* uses neither option) in its own terminal, in the file's folder, with `JAIC_STDLIB` set when configured. *Restart Language Server* stops and starts the client (also done when a path setting changes). *Show Output* opens the *Jai* channel; server traffic goes to *Jai Language Server* (`jai.trace.server`).

## How to change it

```sh
cd editors/vscode
corepack enable           # once: provides the pnpm version pinned by packageManager
pnpm install              # node_modules stays untracked (.gitignore)
pnpm run build            # grammar, schemas, dist/extension.cjs
pnpm run lint             # oxlint, tsc, generated files up to date
pnpm test                 # unit tests (node --test) and grammar tests
JAILSP=../../target/debug/jailsp [JAIFMT=../../target/release/jaifmt] pnpm run test:e2e
pnpm run package          # jacket-vscode-<version>.vsix
code --install-extension jacket-vscode-<version>.vsix
```

For development, open `editors/vscode` in VS Code and run the extension host (F5) after `pnpm run watch`.

- **Grammar**: edit `scripts/build-grammar.ts`, run `pnpm run build`, add assertions to `test/grammar/*.jai` ([vscode-tmgrammar-test](https://github.com/PanAeon/vscode-tmgrammar-test) syntax: `^` under the tested columns, `<-` for column 0). `scripts/tokenize-corpus.ts` tokenizes every `.jai` file in `examples/` and `stdlib/` (or the paths given) and fails if one ends inside a string, comment or here-string, or has an `invalid` token; run it on `corpus/upstream` too after a big change. Keep the grammar derived from the compiler's lexer and parser and this repository's code.
- **New here-string language tag**: add an entry to `EMBEDDED_LANGUAGES` in `build-grammar.ts` (tags, a short name for `meta.embedded.block.<name>`, the grammar scopes to include, the VS Code language ID; check the scope names in VS Code's `resources/app/extensions/*/package.json`), the same tags in the same order to `LANGUAGE_TAGS` in `crates/jai-language-server/src/here_string.rs`, and, if the playground supports the language, to its table. `pnpm run build` rewrites the grammar and `package.json`'s `embeddedLanguages`; it fails while the Rust list differs. Grammar tests can only see grammars this extension ships, so test another language's body against a stand-in in `test/grammar/stubs/` (passed with `-g` in `test:grammar`). Avoid tags that are common generic terminators.
- **New directive or keyword**: add it to the lists at the top of `build-grammar.ts`. Unknown `#names` are still highlighted as directives.
- **New jailint rule**: nothing to do here; `pnpm run build` regenerates `schemas/jailint.schema.json` from `crates/jailint/src/rules/mod.rs`, and `pnpm run lint` (CI) fails while it is stale.
- **New jaifmt.toml key**: add it to `build-schemas.ts`.
- **New release platform**: add one row to `RELEASE_ASSETS` in `src/toolchain.ts` (the full archive name). A unit test compares it with the matrix in `.github/workflows/release.yml`, so CI fails until both agree.
- **New server command or custom request**: handle its result in `ExpansionDocuments.handle` (middleware) or register it in `extension.ts`.
- **Icons**: `scripts/build-icon.ts` (`pnpm run icons`) writes `images/icon.svg`, `images/jai-file-dark.svg` and `images/jai-file-light.svg` from the playground's Jai file glyph (a rounded tile with a `J` cut out, 16x16, even-odd fill) and renders `images/icon.png` (256x256, transparent) with `@resvg/resvg-js`. The colour is the playground's `color-mix(in oklch, var(--red) 62%, white)` with `--red: oklch(63.259% 0.24086 31.631)`, computed in the script (`#ff8e78`); the light-theme file icon uses the red itself (`#fa2b03`). `pnpm run lint` fails when the SVGs are stale; commit the PNG with them.
- **Screenshots** (`images/hover.png`, `completion.png`, `asm-completion.png`, `lint.png`, `quick-fix.png`, `error.png`, `formatting.png`, shown by `editors/vscode/README.md`): `JAILSP=... JAIFMT=... VSCODE_EXECUTABLE=".../Visual Studio Code.app/Contents/MacOS/Code" pnpm run screenshots` on macOS. `test/screenshots/run.ts` opens a real VS Code window with a throwaway profile (`--user-data-dir` and `--extensions-dir` in a temp folder) on `test/screenshots/workspace/`; `suite/index.ts` sets up each scene with editor commands and captures only that window (`screencapture -l<id>`, the id from `window-id.swift`, restricted to the VS Code processes above the extension host), then scales it to 1200 px wide. Add a scene there and a line to the README. The README links images by `raw.githubusercontent.com/.../main/...` URLs, which the Marketplace and Open VSX show as is; the `.vsix` itself carries only the icons.
- **Dependencies**: pnpm, pinned by `packageManager` in `package.json` (CI installs it with `pnpm/action-setup`, locally `corepack enable`). Every npm package, transitive ones included, and that pnpm release must be at least 14 days old, as for Cargo ([dependency policy](dependency-policy.md)). `pnpm-workspace.yaml` sets `minimumReleaseAge: 20160` (minutes), so `pnpm add -D -E <pkg>@<version>` refuses anything younger; `node scripts/check-dependency-age.ts` checks every entry of `pnpm-lock.yaml` and the `packageManager` version against the registry, and CI runs it before `pnpm install --frozen-lockfile`. The same file lists the packages whose install scripts may run (`allowBuilds`: none; rolldown works from its platform package, and keytar and vsce-sign are not used to package or publish with a token). `@types/vscode` must not be newer than `engines.vscode` (vsce refuses to package otherwise).
- **Lint rules**: `oxlint.config.ts` (oxlint's `defineConfig`) enables oxlint's `correctness` and `suspicious` categories with the eslint, typescript, unicorn and oxc plugins, as errors (`--deny-warnings`). Unused arguments may start with `_`; empty `catch` blocks are allowed.

Gotchas:

- `jaifmt --stdin` ignores `ignore` globs and has no `--color` option in 0.3.0; the extension handles the first and does not pass the second.
- The integration tests start VS Code with a short `--user-data-dir` because macOS limits socket paths to 103 bytes; `VSCODE_EXECUTABLE` uses an installed VS Code instead of downloading one into `.vscode-test/`.
- `vsce` needs a `LICENSE` next to `package.json`; `pnpm run package` copies the repository's (untracked in `editors/vscode`).
- **Build and tooling**: `rolldown.config.ts` is the only bundler config. `rolldown -c` bundles `src/extension.ts` to `dist/extension.cjs` (CommonJS, `vscode` external, `vscode-languageclient` bundled, source maps); `--environment PRODUCTION` minifies and drops the map (`pnpm run package`), `--environment TESTS` transpiles `src/` and `test/` file by file to `out/**/*.cjs` (`pnpm run build:tests`) for the unit tests, the integration tests, which VS Code's extension host loads as JavaScript, and the screenshot runner. `pnpm run watch` is `rolldown -c --watch`. `package.json` has `"type": "module"` so that Node loads `oxlint.config.ts` and `scripts/*.ts` as ES modules; the extension and test output is therefore `.cjs`, and `main` points at `dist/extension.cjs`. The scripts run with `node scripts/x.ts` (Node 24 strips the types, so they use erasable TypeScript only: no enums or parameter properties) and `tsc` checks them with `src` and `test` (`tsconfig.json` uses `module: preserve`). The unit tests are still built first because the sources use extensionless imports and `__dirname`.
- `vsce package` runs with `--no-dependencies`: everything the extension needs is bundled into `dist/extension.cjs`, and without the flag vsce runs `npm list`, which fails on pnpm's `node_modules` layout.
- pnpm passes the arguments after the script name through without `--`: `pnpm run package -o out.vsix`.

Files: `toolchain-checksums.json` (written when the extension is packaged, not committed: compiler version and its pinned archive hashes, `{ version, sha256: { <asset>: <hex> } }`; `node scripts/pin-toolchain.ts --toolchain-version X.Y.Z [--extension-version X.Y.Z] --sums SHA256SUMS`, or `--archives DIR`; it pins the `jacket-*` archives), `package.json` (extension version), `jaifmt.toml`, `jailint.toml` and `jai.toml` (`schemas/jai.schema.json`: `build_files`, `import_path`).

Test environment variables: `JAILSP`, `JAIFMT` (unit and integration tests), `VSCODE_EXECUTABLE`.

### CI and releases

The `vscode-extension` job in `ci.yml` checks npm and Cargo dependency ages, installs with `pnpm install --frozen-lockfile --ignore-scripts`, runs `pnpm run lint` and `pnpm test`, builds a debug `jailsp`, runs the integration tests under `xvfb-run` (with a stand-in formatter, `test/e2e/fake-jaifmt.ts`, since building jaifmt needs LLVM) and uploads the `.vsix` as an artifact.

In `release.yml`, the `vscode` job packages `jacket-vscode-<editor-version>.vsix`: the editor version defaults to the compiler tag, and a manual `editor_version` can advance it independently. `scripts/pin-toolchain.ts` stores the compiler version and archive checksums separately from the extension manifest version. The GitHub release attaches the VSIX and includes it in `SHA256SUMS`. Marketplace and Open VSX publish that same package with `--skip-duplicate`; a repin therefore requires a new editor version because store releases cannot replace an existing version. A manual run without a tag builds an artifact but publishes nothing. Forced tag updates also skip publishing; dispatch with the compiler `tag` and a fresh `editor_version` to repin checksums safely.

### Publishing

Publishing needs accounts only the repository owner can create. Until the secrets exist, the publish steps print that they skipped. One-time setup:

1. **Marketplace publisher.** Sign in at <https://marketplace.visualstudio.com/manage> with a Microsoft account and create the publisher `matteopolak` (the `publisher` in `package.json`).
2. **Marketplace token.** In Azure DevOps (<https://dev.azure.com>, any organization), *User settings → Personal access tokens → New token*: organization *All accessible organizations*, scope *Marketplace → Manage*. Check it with `pnpm exec vsce verify-pat matteopolak`.
3. **Open VSX.** Sign in at <https://open-vsx.org> with GitHub, sign the Eclipse Foundation publisher agreement from your profile, and create an access token (*Settings → Access Tokens*). The release workflow creates the `matteopolak` namespace if it does not exist yet.
4. **Repository secrets.** *Settings → Secrets and variables → Actions*: `VSCE_PAT` (step 2) and `OVSX_PAT` (step 3).

The next tag release then publishes the same `.vsix` it attaches to the release. The listing (display name, description, categories, keywords, icon, dark gallery banner, repository, homepage and issue links) comes from `package.json`, and the page from `editors/vscode/README.md`. The Marketplace requires a `name` (and display name) no other extension uses, across all publishers: another publisher's extension is already named `jai` and displayed as *Jai*, so 0.4.0's Marketplace publish failed on the display name and 0.4.1's on the name. That is why the extension is `jacket`, displayed as *Jacket*, on both stores. The Marketplace and Open VSX badges in the repository's `README.md` show a version once the first publish has gone through. To publish an existing release by hand:

```sh
cd editors/vscode && pnpm install --frozen-lockfile
gh release download v0.4.2 -p 'jacket-vscode-*.vsix'   # 0.4.2 or later: older ones are named jai-vscode
VSCE_PAT=... pnpm exec vsce publish --packagePath jacket-vscode-0.4.2.vsix
pnpm exec ovsx create-namespace matteopolak -p "$OVSX_PAT"   # once; "already exists" is fine
pnpm exec ovsx publish jacket-vscode-0.4.2.vsix -p "$OVSX_PAT"
```

The release asset keeps the name `jacket-vscode-<version>.vsix` whatever the extension's `name` is; the stores read the ID from the manifest inside, not from the file name.

### The old extension IDs

The extension was `matteopolak.jai` up to 0.4.1 (Open VSX only) and `matteopolak.jai-toolchain` after. Editors never move an installed extension to a new ID, so old installs keep working until uninstalled. All of them contribute the same language, settings and command IDs, and `registerCommand` throws on a duplicate, so whichever activates second would fail. `activate` in `src/extension.ts` therefore checks `OLD_EXTENSION_IDS` first: if any is installed, the new extension registers nothing, offers to uninstall them (`workbench.extensions.uninstallExtension`), then offers a window reload. Drop an ID from the list once few installs remain.

After the first `matteopolak.jacket` publish, deprecate the old IDs:

- **Open VSX** has no publisher-side setting. ## Dependencies

- Runtime: VS Code 1.91 or later, `vscode-languageclient` (bundled into `dist/extension.cjs` by Rolldown, so the `.vsix` has no `node_modules`), the system `tar` for downloads, and the toolchain itself (`jailsp`, `jaic`, `jaifmt`).
- Development: pnpm, TypeScript, Rolldown, oxlint, `@vscode/test-electron` and mocha (integration tests), `vscode-tmgrammar-test`, `vscode-textmate` and `vscode-oniguruma` (grammar tests), `@vscode/vsce` and `ovsx` (packaging and publishing), `@resvg/resvg-js` (the PNG icon).
- Grammars for here-string bodies: VS Code's built-in language extensions (SQL, JSON, HTML, CSS, JavaScript, TypeScript, Python, shell, C/C++, Objective-C, Rust, XML, YAML, Markdown, Lua, HLSL), optional third-party ones (`source.wgsl`, `source.glsl`, `source.metal`, `source.toml`), and the bundled `syntaxes/wgsl.tmLanguage.json` and `syntaxes/toml.tmLanguage.json`, written for this extension.
- Internal: jailsp's protocol (`crates/jai-language-server/src/protocol.rs`: capabilities, `jai.showExpansion`, `jai.showPolymorphs`, `jai/source`, `jailint.toml` documents), jailint's rule table, jaifmt's `--stdin` contract and `jaifmt.toml` keys, and the release archive names in `release.yml`.
