# Upstream corpus

## What it is

Pinned snapshots of open-source Jai projects that `jaic` is measured against: applications (Focus, Jails, The Way to Jai, Vk-Engine, sgpu, chess-jai, forbear, ...), their dependencies (jai_parser, Linalg, Jolt-Jai, Tracy's client) and libraries (metaprogramming libraries such as match-jai and yield-jai, rluba's family such as jaison, uniform and hyperserve, and libraries with their own tests: reflector, jai-format, jai-protobuf, toml-jai, jai-xml). The authoritative lists are `REPOSITORIES`, `DEPENDENCIES`, `LIBRARIES` and `STAR_REPOSITORIES` in `tools/fetch_upstreams.py`. jaithon is excluded: it is its own language in `.jai` files.

Files live in the gitignored `corpus/upstream/`; the committed `corpus/upstreams.json` records each repository's exact commit, its selection and how many files it pins. It lists no files: the commit fixes every file's content, and `select_paths` in `fetch_upstreams.py` fixes which files are taken, so the fetcher recomputes the list from the Git tree (`pinned_blobs`, which needs no file contents) and checks each file against its Git object id. A change to the selection rules therefore shows up in review as a code change and as changed `file_count`s, not as a file list. Both the corpus and the Git cache live in the main checkout (via the Git common dir), so worktrees share them.

## How it works

`tools/fetch_upstreams.py` downloads the pinned `.jai` files, READMEs, licences, C-family sources (`NATIVE_SOURCE_SUFFIXES`, for native-library builds) and compile-time data files (`RESOURCE_PREFIXES`) into `corpus/upstream/<owner>--<repo>/`. It never builds or runs a project.

- Existing pins are kept. `--since YYYY-MM-DD` (default 2025-10-01) is the recency cutoff for new repositories; `DEPENDENCIES`, `LIBRARIES` and `STAR_REPOSITORIES` are exempt.
- Binaries are never pinned: `is_forbidden_file` refuses executable, library, object and archive suffixes (`BINARY_SUFFIXES`) and, after download, files that start with an executable or archive header (`BINARY_MAGIC`), whatever their name. Only `.jai`, C-family sources, READMEs and licences are taken from a star repository (no `RESOURCE_PREFIXES`), under the 8 MiB cap. Every file, new or already on disk, must hash to its Git object id from the tree (`blob_id`), so a truncated download (`toolkit/download.py` also compares the body with `Content-Length`) fails the fetch instead of being pinned.
- `MODULE_LINKS` symlinks dependencies into consumers' `modules/` and libraries imported by name into `corpus/upstream/_modules/` (cases pass `-I ../../_modules`).
- `SOURCE_PREFIXES` limits a repository to some directories (Tracy: only `public/`); `MAX_FILE_BYTES` raises the size cap for a file (chess-jai's network).
- Building the projects leaves libraries and generated files next to the sources, so a hash mismatch or stray file after a build means restore with `fetch_upstreams.py` and give the case a `setup` step that avoids the write.

Entry points that work are sweep cases in `tools/upstream-cases.json` ([testing](testing.md)); `check` mode is used for heavy ones, with `setup` commands for prerequisites. Where a project documents its output, the case carries an `expect` record:

```json
{"id": "ttwj-16-16.3-enum-specified", "mode": "run",
 "path": "Ivo-Balbaert--The_Way_to_Jai/examples/16/16.3_enum_specified.jai",
 "expect": {"stdout_ordered": ["enum 'Direction' is", "specified"],
            "source": "The_Way_to_Jai `// =>` annotations, lines 20, 22, 26"}}
```

A case that cannot run on every host carries `only` (a list of platform names, e.g. `["linux-x64"]`) and `only_reason`; the sweep reports it as platform unavailable elsewhere instead of failing.

A case whose own source has a genuine error (a removed API, a deprecated directive, wrong arity) carries `disabled` with a short reason. The sweep and the smoke run skip it and count it separately; manifest rows of the stdlib and compiler test catalogues accept the same key.

Expected values must come from the project (docs, tests, golden outputs written by people who ran Jai), never from jaic's own output, which only freezes current behaviour. A missing expected line is a jaic bug until shown otherwise; reject an annotation only when the book is wrong about current Jai. Per-example outputs from open-jai are not used: it produced them with its own reimplementation.

## Smoke tests

`tools/corpus/upstream_smoke.py` builds each project with its own entry point and runs it unattended. Checks live in `tools/corpus/upstream-smoke.json` (validated by `tools/corpus/test_upstream_smoke.py`); CI runs them in the `upstream-smoke` job of `ci.yml` on linux-x64, linux-arm64, macos-arm64 and windows-x64.

```sh
PYTHONPATH=tools python3 tools/fetch_upstreams.py --only $(PYTHONPATH=tools python3 tools/corpus/upstream_smoke.py --jaic x --projects)
PYTHONPATH=tools python3 tools/corpus/upstream_smoke.py --jaic target/release/jaic              # every check for this machine
PYTHONPATH=tools python3 tools/corpus/upstream_smoke.py --jaic target/release/jaic --filter focus -v
```

Each check copies its project into a scratch directory and runs steps in order. Step `kind`: `jaic` (`outputs` must exist, `contains`/`ordered`/`not_contains` check output), `run` (default; `stdin`, `exit`), `gui` (must still run after `seconds`, and the screen must change between screenshots taken before and after start), `serve` (free port via `{port}`, fetch `get`), `lsp` (`initialize` over stdio). `needs` runs a step only if a program was built, `only`/`skip` limit platforms, and a check with `only`/`skip` or no steps is a documented skip with a reason. Servers, editors and games need `serve` or `gui`, never a bare `run`. GUI programs run under `xvfb-run` on Linux; on Windows Mesa's software `opengl32.dll` is copied beside them.

Known deviations: Focus builds with `first.jai - release` and, on Windows, is built but not run (Mesa reports a GL error its Simp backend turns into a breakpoint); reflector's `build.jai` also builds a Windows-only benchmark, so the check builds `tools/corpus/upstream-drivers/reflector-tests.jai` instead, and its case patches uninitialised arrays upstream leaves undefined; jai-tracy compiles libtracy from the pinned client instead of running `generate.jai`; toml-jai's `tests.jai` spawns a `jai` per example, so the check runs each itself.

Accepted on purpose: some cases pass although the reference compiler rejects them, because jaic is deliberately more lenient there, and says so with a warning for each ([leniencies](../language/leniencies.md)): The Way to Jai's `#place`, `Enum.loose`, top-level `#foreign_library`, `#must` on a return type, `#ifx ... then a; else b;`, `*T.{...}` taken as the address of a literal and a local procedure used before its declaration; unotest's `get_plugin`, which has the parameters of one a module it imports exports (`declaration-hides-import`). Hyperserve's `#assert` on `type_of` of a local declared the line before is listed too, but no reduction of it is rejected by the reference, so it has no warning. Cases that load a `#module_parameters` module as a program file stay disabled, since jaic rejects that too.

Trying entry points: `JAIC_UPSTREAM_CASES=<file> jaic_sweep.py ... upstream` reads cases from another file (a scratch copy holding only the cases being triaged), so experiments never touch `tools/upstream-cases.json`.

Platform-restricted cases: a case that can only run on some hosts names them in `only` (with `only_reason`) in `tools/upstream-cases.json`; elsewhere it reports `PLATFORM_UNAVAILABLE`. The x64 steps of `ci.yml` do not list ids: `tools/corpus/select_upstream_cases.py --platform linux-x64|windows-x64` selects every enabled case whose `only` names that platform (`--ids`, or `--repos` for `fetch_upstreams.py --only`), and `jaic_sweep.py upstream --only-platform P` runs them, so a new Windows-only case needs no workflow edit. Cases restricted to x86-64 hosts: the CPUID and `#asm` examples of The Way to Jai, `ttwj-30-jai-raylib-build`, `chess-jai-ui-check`, `chess-jai-engine-check`, and the four `vk-engine-*-check` cases, which pass `-os linux -cpu x64` because the non-x64 `Default_Allocator` has no `initialize_if_needed`, which Vk-Engine calls. `tools/ci/ci_changes.py` runs the Windows job when the case list or the pins change.

Cross-target compile-time code: in a cross build a plain `#run` executes on a host twin (`docs/compiler/compile-time-host-execution.md`), so `-os linux` on a Mac still starts processes, queries files and detects the CPU on the Mac. Vk-Engine's `Build.jai` (`run_command`) and XChatger's `first.jai` (`file_exists`, a child workspace) therefore check on macOS too.

Projects that do not fully work, and why: raylib-jai (examples are check-only: its prebuilt raylib and raygui libraries are binaries, not pinned, and `native-libs.md` does not build raylib, so nothing links or runs; all of its examples check), Vk-Engine (checks with `-os linux -cpu x64`, no macOS support upstream), jai-postgres and jai-redis (need a database or server), Photon (Windows-only; `photon-check` type-checks `source/main.jai` with `-os windows -cpu x64` through `tools/corpus/upstream-drivers/photon-check.jai` and checks; the driver adds a stub for the options procedure the project's build program would write), KodaJai (its modules and the other kujukuju libraries are pinned and reached as `-I` module paths; `tests/main.jai` and `input_poll_tests.jai` pass, but `module.jai` calls the undefined `create_cubemap` and the deferred example passes `bool` for an enum parameter, so those two are disabled), no_api (its entry point loads a file missing upstream), ui_builder (link needs an unpinned prebuilt `libslang`), sgpu (examples build on macOS after `tools/native/build_slang.py`; mesh shaders need a driver MoltenVK lacks), wait_group on Linux (upstream typo: `signal` where `it` was meant), The Way to Jai (examples that check but do not run are Windows-only, written for an older Jai, interactive, or deliberately failing).

## Sandbox

Everything under `corpus/upstream` is unreviewed third-party code, and compiling it runs its compile-time code (`#run`, build programs). So `jaic_sweep.py upstream` and `upstream_smoke.py` run every `jaic` invocation, setup command and produced executable through `tools/bench/sandbox.py`: no network, writes only to the case's scratch copy, reads limited to the system, the `jaic` build tree, `stdlib/`, `JAIC_NATIVE_LIBS` and `corpus/upstream`. macOS uses `sandbox-exec`, Linux `bwrap` (CI installs bubblewrap and lifts Ubuntu's unprivileged-namespace restriction). Servers and X11 clients get loopback (`Sandbox(loopback=True)`); the GUI step on Linux also reads `/tmp/.X11-unix`, and a Mesa DLL directory is read when given. Build and `run_after` cases work in a scratch copy of their project with the other repositories linked in, so a build that writes into its tree never touches the corpus.

Where no sandbox exists (Windows) the runs are unconfined on CI runners only: `tools/corpus/upstream_sandbox.py` refuses outside `CI` unless `--no-sandbox` is passed explicitly. Extra reads or writes a case needs are added as exact paths, never by opening the sandbox wholesale. `tools/corpus/test_upstream_sandbox.py` covers the policy, the wrapping and the write confinement.

## Star-qualified repositories

`STAR_REPOSITORIES` holds every `language:Jai` repository with at least `STAR_THRESHOLD` (5) stars, however old (found 2026-10-20 with `gh search repos --language=Jai --stars=">=5" --limit 200`). It also holds repositories found with code search whose language GitHub reports as something else or as none (a `.gitattributes` `linguist-language` override, or Jai outweighed by C, C++ or generated bindings). They are unreviewed, so:

- **Scan first.** `tools/corpus/scan_upstream.py [owner--repo ...]` reads the pinned files (never runs anything) and prints a per-repository risk: process spawning, networking (sockets, URLs, IP literals), deletes and writes outside the project, credential and home paths, environment access, unusual `#foreign_library` names, `#asm`, base64/hex blobs and byte arrays (decoded and checked for executable headers), obfuscated identifiers, binaries. A finding is *build* context when it sits in a `#run`, a procedure a `#run` calls, or a build program (`first.jai`, `build.jai`, files using `set_build_options`), and *runtime* otherwise: the same call is `high` at build time and `medium` or `low` in ordinary runtime code. Exit status 1 means a `high` finding; `--json` keeps the lines. `test_scan_upstream.py` covers the rules.
- **High risk is read, not skipped.** A repository with a `high` finding is pinned only after a person has read those lines. The 15 repositories whose build scripts spawn processes, delete files, download or use compile-time `#asm` were pinned that way as sandbox-only cases. After triage, the repositories whose build scripts still launch external programs, download or delete outside their tree keep `"review": "pending"`. Medium is pinned; the reasons are in the report.
- **Excluded** (`EXCLUDED_REPOSITORIES`): jaithon (its own language), this repository, and star-qualified repositories whose `.jai` files are incidental samples, fixtures or licence texts, or are pre-release syntax experiments. Vendored copies of official Jai modules are never pinned (`vendored_official_module`, by directory and file name alone, compared without case; `OWN_MODULE_PREFIXES` lists the reviewed directories that only share a name), and forks of an already-pinned upstream, repositories without `.jai` source and repositories that are mostly prebuilt binaries are left out of the list.
- **Review gate.** A new star repository's cases carry `"review": "pending"` until someone has read the code the cases reach and fixed their entry points (cases that need a driver point `files` at `tools/corpus/upstream-drivers/`). `select_upstream_cases.py` never selects a pending case (so the Windows and linux-x64 jobs, which run unconfined, cannot pick it up even if it were given `only`), and `jaic_sweep.py` reports a pending case as unavailable unless the run is inside `tools/bench/sandbox.py`: `--no-sandbox` and CI do not excuse it. `test_star_corpus.py` checks that pending cases are unrestricted, that no reviewed case borrows a pending repository, that no smoke check uses a star repository, and that no pin holds a binary.

## How to change it

- **Add a project:** add it to `REPOSITORIES`, `DEPENDENCIES` or `LIBRARIES`, run `fetch_upstreams.py`, review and commit `corpus/upstreams.json` (never `corpus/upstream/`), add entry points to `tools/upstream-cases.json`, and a smoke check if it can run. Prefer projects that check themselves. A project importing unpinned modules from the same author can only be tested once those are pinned (`LIBRARIES` plus `MODULE_LINKS`).
- **Add a star repository:** append it to `STAR_REPOSITORIES`, fetch, run `scan_upstream.py` on it and read any `high` finding before committing the pin, then add `"review": "pending"` cases.
- **Find candidates (code search):** GitHub's language label misses repositories that override it or are mostly another language. Run `<term> extension:jai size:<bucket>` queries (`gh search code`, or the REST code-search API) over narrow size buckets, since one query returns at most 1000 files, collect the repositories, keep those with at least `STAR_THRESHOLD` stars, and drop ones already listed in `STAR_REPOSITORIES` or `EXCLUDED_REPOSITORIES`. Keep Jai projects and real Jai components; leave out repositories whose `.jai` files are samples or fixtures (linguist, editor themes, grammars) and list those in `EXCLUDED_REPOSITORIES` with a one-line reason.
- **Find candidates:** `gh search repos --language=Jai --stars=">=20" --updated=">=<date of last pass>" --limit 100 --json fullName,stargazersCount,pushedAt`; "pushed" in the REST query (`language:Jai pushed:>=...`) means code changed, while "updated" also counts stars and issues.
- **Try it:** entry point is usually `first.jai` or `build.jai` (arguments after `-` select targets). Try `jaic -check`, then a build, then a run, with a release `jaic`. Classify: passes; jaic or stdlib bug (reduce to a test under `tests/compiler/regressions/` and fix); needs native libraries or another platform (`-os linux`/`-os windows` still type-checks); outdated or broken upstream (note the line).
- **Verify on every platform** before trusting a smoke check: `-os` flags only type-check. Push a `tmp/...` branch, run CI there, then delete it.
- The largest projects can also be [benchmark](benchmarks.md) workloads.

## Dependencies

Git, Python 3.11+, network access to GitHub; `gh` (authenticated) for searching; clang for cases that compile vendored C (forbear). Native libraries the projects need come from [native libraries](native-libs.md); `JAIC_NATIVE_LIBS` points builds at them.

The `sgpu-vma-bindings` smoke check runs sgpu's pinned `modules/Vulkan_With_VMA/generate.jai` unchanged on Windows. It requires both debug/release VMA archives and a freshly generated Windows binding file, then type-checks the public module. Setup only recreates the `win` output directory omitted by the source-only fetch and removes the old generated file. This checks BuildCpp's MSVC flags and actual C++ compilation without Slang, a Vulkan driver, or a GPU. The full rendering example remains a separate unavailable check. Checkout runs must first prepare the generator runtime with `python tools/ci/package_bindings_helpers.py --platform windows-x64 --llvm-prefix "$LLVM_SYS_231_PREFIX" --out target/native-libs/windows-x64` (replace the CPU for arm64). This builds the host operations and stages SDK libclang in the normal native library search directory, as release packaging does. The Windows third-party workflow performs that setup. Both Windows CPU names are enabled; the permanent Windows third-party job runs x64, and an arm64 CI runner can select the same check (like every Windows corpus run, it is refused outside CI).
