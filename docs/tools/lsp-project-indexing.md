# Project indexing in the language server

The language server checks source files in their enclosing program, including files loaded by other sources and programs created by a build metaprogram. Opening a fragment first must give it the same context as opening the entry first.

## How it works

Project entries come from `[project] entry` in `jacket.toml`, or the existing inferred entry names (`build.jai`, `first.jai`, `main.jai`, `src/main.jai`, `module.jai`). The server indexes entries while idle, recording the actual sources, generated strings and import directories supplied by their metaprograms. Each entry's compiler checks its inclusion graph. The recorded graph includes imports, `#import,file`, and child workspaces; lexical load closures remain separate because imported names have different visibility. Inferred entries already included by an earlier entry are not checked again as standalone programs. Explicit configured entries remain independent.

An included file uses that recorded program context. Unrecorded inferred entries are probed too, so a file can find its enclosing metaprogram before any other source is open. New build edges invalidate cached loader graphs. Changed loader files are rescanned before a cached graph is used, including when a removed load is restored. Entry selection starts from the requested file, so open loaders cannot change its project context. Source stamps and filesystem dependencies validate recorded graphs after changes. Opening or closing unchanged disk text preserves analyses and discovery caches, including when a preview tab closes one file while opening another. Closing a compiled buffer reuses its analysis only when its former bytes match disk; discarding unsaved edits still requires checking. Buffer edits retain older analyses for responsive requests, while disk notifications invalidate affected analyses. Directory enumeration records dependencies and includes virtual open files. Interrupted indexing leaves the entry pending. Opening a buffer whose exact bytes already have recorded editor facts reuses the indexed analysis, including facts in child workspaces. Newly opened sources without those facts still require checking. Reading an unopened source uses the compiler's replacement decoding for invalid UTF-8, so opening the file cannot change whether a load is considered present. For files that were only tested for existence, reuse also requires proof that they were already present and the new buffer exactly matches disk.

After discovering the graph, the server checks diagnostics for every included workspace file, including closed files. Lints run in batches per program and configuration so interprocedural summaries are shared. A file included by several programs shows the union of what each program reports for it. A finding is not labelled with the entry it came from: the message is the same defect whichever program finds it, so a finding every program makes shows once (equal range, severity, code, message and notes), and one only some programs make still shows, because that program really fails. An open file is checked under every entry that reaches it (`Session::sibling_roots`), also when an edit has thrown its snapshot away; hover, definition and the other requests answer from the first such entry (`Session::project_root`), so they stay the same while diagnostics cover all of them.

A project file that no entry reaches is in no program. The server cannot type check it in any context, so for a closed file it reports only its syntax diagnostics (and unreadable `#load`s), and for every such file, open or closed, an information diagnostic (`not-in-program`, source `jaic`) on the first line saying so, instead of errors for names a loader might declare. An open one keeps being checked on its own, as before. "Reaches" means the file is in an entry's `#load` closure, in a project module the entry imports, named by `#import,file` or `#import,dir`, or recorded by a build metaprogram. The note appears only once every entry has been run (an untrusted workspace, or an entry that has not finished indexing, says nothing), only for files under the project's base folder, and never in a workspace with no entry. It goes away when a `#load` or entry change makes the file reachable. The set is cached in `session/workspace_diagnostics.rs` and recomputed when the program graph, `jacket.toml` or a file no program holds changes (`Sources::unreached_files` in `auto_import/programs.rs`). Completed snapshots serve workspace diagnostic pulls or push publications, keep explorer warnings when files close, and let a newly opened matching buffer reuse diagnostics immediately. Edits invalidate affected snapshots; interrupted batches never publish partial results. Indexing remains active until this diagnostics pass finishes.

The native transport uses standard `window/workDoneProgress/create` and `$/progress` messages. It waits for the client's token acknowledgement, then sends a begin notification before checking. The title is `jailsp`. Begin and each report carry a `percentage` and a `done/total` message such as `3/17`. The count is the work the server actually does: entries analysed, then diagnostic roots checked, as one combined total. The percentage and the done count never go back within one begin/end, even when a build metaprogram adds entries or an edit restarts a phase; the total shown may grow. Until the first step finishes the message is `indexing` at 0%. The indicator disappears when project checks finish. Publishing cached diagnostics or summarizing code lenses does not start the indexing indicator. VS Code and Neovim can display these through their LSP progress integration. Clients that do not support work-done progress keep receiving normal language features.

## How to change it

`session/indexing.rs` schedules entries, and `session/workspace_diagnostics.rs` caches whole-program diagnostic batches. `auto_import/programs.rs` selects their owning program, and `session/compile.rs` records build facts. Keep compiler-recorded edges authoritative and invalidate derived loader graphs when those edges change.

Lifetime lint queries memoize shared temporary-value paths by value and depth; write-summary propagation checks for interruption so edits can stop the diagnostics batch.

`protocol/progress.rs` owns the progress lifecycle and the monotonic percentage; `Session::indexing_counts` combines the counts that `index_workspace` and `index_workspace_diagnostics` record; `main.rs` flushes its begin notification before starting idle work. Progress must not block requests while indexing is interrupted by new input. Feature refreshes are sent when indexing completes, rather than after each attempted or interrupted step: a refresh response is itself input and must not restart the same unfinished work. Checks already completed for code lenses also satisfy indexing. Background workspace diagnostic polls and server-request acknowledgements wait for ongoing checks; interactive messages interrupt them. Framing happens on the input thread so partial frames cannot cause repeated restarts. The native transport registers cancellations for the queued batch, then flushes each reply as it finishes; an expensive diagnostic request cannot hold back hints and tokens already answered earlier in that batch.

Member completion first uses receiver types from the indexed program. A placeholder compile is needed only when that context is missing. Known built-in types and members have no source definition and do not trigger cross-target searches for one. Public type-alias signatures are resolved before module completion so their kind is stable.

The entry set (`Session::workspace_entry_set`) is memoized on the session generation, the index epoch (disk changes and newly recorded build facts) and the workspace folders, so progress checks and idle work do not re-walk the open files' projects. A file changed on disk without a notification is noticed when one of those moves; `tests/entry_traversals.rs` bounds the walks.

Use the [graph audit](lsp-graph-audit.md) to check every included repository file in several open orders.

## Configuration

```toml
[project]
entry = ["first.jai"]
import_path = ["modules"]
```

Explicit entries override inference. Existing compile-time budgets and workspace trust settings still apply. The checker has no executable output backend; indexing follows build metaprograms without linking their output.

## Dependencies

`jaic::project`, the shared lint compiler and sandbox, the semantic analysis cache, workspace build observers, and the client's standard LSP work-done progress support.
